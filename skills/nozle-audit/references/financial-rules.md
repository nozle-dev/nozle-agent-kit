# Financial and runtime integration rules

These rules hold whatever the API looks like this week. The facts they need (which call, which field, which code, which default) come from the docs and the installed SDK, as [docs-lookup.md](docs-lookup.md) describes.

## Principles

- Derive the Nozle customer and organization from authenticated backend identity. Secret keys live on the server only. The external customer id is the application's stable id, never an email address or another personal value (it outlives an erasure; see `/api/create-customer`).
- One billable event per successful operation, sent at its success boundary: after the result exists, before the response is final.
- One primitive per purpose, never two for the same consumption. A metered action without credits records a usage event after it succeeds. A credit-backed action spends through the credit call, which is both the gate and the charge, so no usage event follows it. Work whose cost is known only afterwards, with several spenders on one balance, holds first, then finalizes with the actual usage or releases. An access check reserves nothing and is not a gate for credit-backed work. Cost events record serving cost and never bill. Read each primitive's page (docs-lookup.md, choices 4 to 7) before choosing.
- Every unit has one stable identity: its transaction id or idempotency key comes from a business or request id, and its timestamp is fixed when the unit is first stored. Both stay identical on every retry, from any process. A retry with the same key and body replays the first answer; a changed body is a conflict.
- Select the subscription explicitly when more than one can be active, and surface the ambiguity instead of picking one.
- Treat plan grants and purchased credits as distinct sources. Preserve decimal precision, expiry and consumption rules.
- Fulfill checkout only after authoritative payment confirmation (a verified webhook or a server-side status read), never after a browser redirect. Process webhooks idempotently, deduplicated on the delivery id the docs name.
- Respect what the account cannot model (the docs and the account read say what that is) and state it as a gap; never emulate it in a way that charges differently.

## Credentials stay with the user

- Never create, request, paste, read, or store a Nozle API key, and never write a key value to any file. The user makes keys in the dashboard. To confirm the user's keys work, run `nozle-check key <app directory>` (or `node <skill folder>/scripts/nozle-check.mjs key <app directory>`) as one plain command: it reads the keys from the environment, `.env.local` or `.env` itself, asks Nozle's plan catalog (read-only, nothing billable), and prints only each variable name, its source and the verdict, never the value. Run it when the user says the keys are in place, and report the verdict: a rejected key goes back to the user's steps.
- Add every variable the new code needs to `.env.example` with an empty value and a one-line comment (the server-side secret key variable the SDK page names, and a separate publishable-key variable only if client code needs one). Read them from the environment in code, and make the code fail with a clear message when one is unset. Leave `.env` and other real env files untouched.
- End the hand-off with the dashboard steps the user must do themselves, in order, before the integration works: create the API key(s) in the Nozle dashboard, copy them into their own `.env`, plus each missing account setup item from the coverage map (plans, meters, provider connection, webhook endpoint, and the like). List a step only when this app needs it.
- Offer the first-event check as the last user step. The user runs `node <installed skill folder>/scripts/nozle-first-event.mjs --customer <id> --event <meter code> --subscription <id>` from their own shell: it prints the request and sends nothing; `--yes` sends one real, billable usage event to the Engine with the secret key from their environment. The agent never runs it, with or without `--yes`: the guard hooks deny any command that names it. Running it twice sends the identical event (same transaction id and timestamp), so it counts once.
- Amounts from Nozle are minor units. Convert them for display only, never for totals, and give the currency's decimal digits a fallback (for example `formatter.resolvedOptions().maximumFractionDigits ?? 2`) so strict TypeScript compiles.
- If the application keeps its own balance next to Nozle, make that deduction idempotent too: record the transaction id with a unique key in the same database transaction as the deduction, and decrement atomically (in SQL, under a row lock) rather than read, subtract and save. Nozle's key protects only Nozle's side.
- **Billing goes through what Nozle offers.** Payments, subscriptions, renewals, plan changes, cancellations and credit grants run through Nozle checkout and Nozle subscriptions, with a payment provider Nozle documents. The plugin never builds external billing authority (billing-state imports with external authority, opening-balance imports): Nozle cannot renew, change or cancel such a subscription, so the app would need a second billing engine. When the product's provider is not one Nozle offers, the options are moving that job to Nozle with a supported provider, or leaving payments and paid-plan credits out of this integration (see the payment provider question in decision-questions.md).

## Refusals and errors

Nozle answers every refusal with a status and a machine-readable `code`. The endpoint's page and `/api/errors` list each code and the action to take. Before writing a call, read that list; then branch on the exact status and code (in an SDK, the error class and code fields its types declare), never on message text. A refusal you have not read about is handled as a failure for review, not guessed.

Sort each documented refusal into one of these kinds and handle it as the kind says. Self-review: `conflict-409`, `error-types`, `retries`.

- **Transient** (a network error, a timeout, a 5xx, a 503 with `Retry-After`, a rate limit): retry with the same key, body and timestamp. The SDKs retry these themselves by default; read the default count in `/sdks/<lang>/installation`, size timeouts and fail-open budgets for every attempt, and do not stack an app retry loop on the SDK's. An in-process retry is not durable settlement. After a timeout the charge may have landed: the unit stays `pending` with its key (see "An uncertain charge stays pending").
- **Product refusal** (a used-up spend limit, a unit limit, too few credits, a customer blocked for unpaid invoices or by staff): deny the action, show the reason and the customer's next step, and never retry it or fail open on it. A denial that the API returns as data (`allowed: false` with a reason) is the same kind.
- **Customer blocked** (`402 customer_payment_overdue`, `402 customer_blocked`): this is a normal state of a customer, not a configuration error, so it never raises an operator alert. Show the customer a way to pay: their unpaid invoices with a pay link per invoice, or the customer billing page (read `/guides/billing/dunning` and `/guides/billing/checkout#pay-links` for the current options). A staff block is not lifted by paying, so it shows "contact support" instead. The usage of a blocked customer is refused and not queued; what the app does with work that already ran for them is a user decision (`blocked-usage`: keep the unit pending and send it after the block lifts, or let it go).
- **Late usage** (`409 period_invoiced`): the unit's timestamp falls in a billing period whose invoice is final. Nothing was stored or spent, and replaying the stored timestamp is refused forever, so a settle job that keeps replaying it never bills the unit. Handle it the way the user chose once (`late-usage`), from the late-usage section of that endpoint's page (`/api/events#late-events`, `/api/usage-track`, `/api/finalize-usage-hold`): resend once with the same key or transaction id and a current timestamp, store that new timestamp with the unit so later retries replay it, and bill it in the current period; or record it for a one-off invoice; or let it go. When the subscription has ended there is no current period, so only the one-off invoice or letting it go remain. A hold refused this way stays open: finalize it again with a current timestamp, or release it.
- **Conflict from a changed payload** (`409 idempotency_key_reused`, `409 transaction_id_conflict`): the same key was sent with a different body, so the code that keeps the payload stable has a bug. It is never proof that the unit was charged. Log it with the request id, mark the unit failed for review, and fix the cause; do not send it again under a new key.
- **Other state conflicts** (a checkout already in progress, a hold already resolved, a voided transaction id sent again, a tax check pending, an archived plan): do what the docs say for that code: wait and re-read the state, use a new id, or pick another plan.
- **Configuration or caller error** (an authentication error, an unknown code, no active subscription or several, a validation error): deny or surface it; never swallow it with a catch-all and never fail open on it.

Fail open (let the action through) only on a transient failure, and only when the user chose fail-open. One unit's permanent failure never blocks other units or the user's later requests: a loop that settles stored units catches each unit's error on its own, records the outcome, and continues. Log the request id with every failure.

## Build traps seen in testing

- **Usage keys come from a business or request id.** Build the idempotency key and transaction id from something that stays the same on every retry: the job and item id, a client-supplied message id, the provider's response id, the inbound request id, or the payment or order id. Never generate it per attempt (`randomUUID()`, `uuid4()`, `nanoid()`, `Date.now()`). When no stable id exists, create one when the unit is first stored and reuse it. Store the unit's timestamp with it: an SDK fills in the time only for a retry inside the same client and process, so a retry from a queue, another process or after a restart must pass the stored one. (self-review: `usage-key`)
- **A client-supplied id is not a billing key by itself.** When the key comes from an id the client sends (a message or request id), the server must also dedupe the work: store the id with a unique constraint and return the stored result for a repeat, without a new provider call. Otherwise a client that reuses one id gets unlimited free work while Nozle dedupes the charge. Without that store, use a server-made id saved with the unit. (self-review: `client-ids`)
- **Streams are billed on provider finish.** Record usage when the provider reports final usage, whether or not the client is still connected, and record it before writing the final chunk to the client. An abort after the provider finished is billed; an abort before it is not. Do not pass the client's abort signal to the provider call: when the client disconnects, keep reading the provider stream to its final usage, then bill (or stop the provider explicitly and bill the usage it reports, when the user chose that). A capture helper records only the usage it saw, and some providers report usage only in the last chunk, so read the capture page for the stack before relying on it. (self-review: `stream-abort`)
- **Use the subscription id that exists.** The code may choose a deterministic external id when it creates the subscription (for example `sub_${userId}`), but when the lookup finds an existing one (made in the dashboard or by another path), store and use that subscription's id; never rebuild the id and assume it matches. (self-review: `subscription-id`)
- **No paid subscription without payment.** Subscribe a customer to a paid plan only after checkout or confirmed payment. One code path owns subscription creation: look up the active subscription first, then create. A free plan is assigned once, at signup. (self-review: `paid-without-payment`)
- **Replacing an existing app balance needs a rollout.** When the application already holds balances or quotas, the scope must have off, shadow and enforce modes and a plan for every existing balance before enforce. Purchased credits have no import, so propose a drain and let the user choose: spend the legacy app balance first and move each user to Nozle when it reaches zero, or keep honoring it beside Nozle until it is spent; never strand it. Schema and model changes must work before their migration runs (a nullable column, code that reads both shapes), so `off` really changes nothing for current users. Off and shadow never create customers or subscriptions and never change an account; shadow only reads and logs, unless the user chose a shadow that also sends usage. Ship the migration file with every schema change. (self-review: `legacy-balance`, `shadow-writes`, `migration`)
- **Nozle owns the period.** Nozle renews the subscription, issues the next grant and applies plan changes and cancellations. The app never creates a subscription per period and never grants a period's credits itself for a customer whose allowance is in Nozle. It follows Nozle's state: the subscription webhooks update the app's own records, and a reconciliation job reads the subscription when a delivery is missed. A plan change goes through Nozle checkout or the subscription change call, never through an app-only plan field. (self-review: `renewal`)
- **An uncertain charge stays pending, never failed.** After a timeout, a network error or a 5xx the charge may have landed. Keep the unit `pending` with its key, body and timestamp and settle it later with the same three; a retry by the user resumes that pending unit instead of creating a new one with a new key, which would charge twice. (self-review: `stuck-unit`)
- **A legacy remainder smaller than one unit is never stranded.** One unit cannot be split across the legacy balance and Nozle, so ask the user and record the choice: let the legacy balance pay the whole unit while any of it remains, or show the remainder and refund or convert it. Never silently charge the full unit in Nozle while the remainder sits unspent.
- **Charge order for work that can fail is a user decision.** Ask which one the user wants and write it in the scope: (a) charge first through the credit call and run the work only when it is allowed; a failed job stays charged unless the app reverses it (an event can be voided while its period is not invoiced; read `/guides/billing/event-pipeline`) or compensates in its own records; (b) hold, then settle: hold the most the work can use, run the work only when the hold is allowed, finalize with the actual usage on success and release on failure or cancel, so failed work costs nothing and concurrent workers cannot overspend; recommend it when the cost is known only after the work and several workers spend one balance; or (c) an advisory check before, the work, then the credit call keyed by the job id after success; concurrent requests can overspend, and when that call is denied the app must record the debt and deny the next request instead of only logging it. Under (b) a finalize above the hold can also be denied (it charges nothing and leaves the hold open), so the same debt rule applies. Never treat a denial as a log line. (self-review: `charge-order`)
- **Async servers.** Under async handlers use the SDK's async client when the installed version has one (see `/sdks/<lang>/installation`); otherwise run the synchronous calls in a thread.
- **Keys that stay unique.** An autoincrement row id repeats across environments and database resets; prefix the key with the environment or use a UUID column created with the row.
- **A money move between two ledgers happens once, enforced by the database.** A drain, renewal or balance move that debits the application's own ledger must, inside the debit transaction, insert a unique claim row keyed by the customer and the period (or re-check the state under a row lock), and compute the amount from rows locked in that same transaction. An amount read before the transaction and used inside it lets two concurrent callers debit twice. (self-review: `ledger-once`)
- **Every pending or uncertain charge has an owner that runs without user traffic.** A job, queue or scheduled task settles pending units with their stored key and timestamp, and records each final outcome (charged, refused with its code, chosen late-usage path) so it never settles that unit again. Settling only inside a request path leaves work unpaid when the customer makes no further request; say who settles a pending unit if this customer never calls again. The same holds at every hop: a service that hands a usage or cost event to another service stores it before sending and retries from that store. (self-review: `pending-owner`)
- **Never call Nozle inside a database transaction that can still roll back.** Charge after the commit, keyed by the committed record. A charge inside the transaction survives a rollback (an overcharge), and an HTTP call inside it holds row locks for its whole timeout. (self-review: `charge-in-transaction`)
- **A key comes from one stored business record whose existence is the billable event.** Ask: can a new billable event ever produce this key again? A hash of content that can recur (the same lead list imported again after a delete, the same prompt text) can, so it is refused; use the id of the stored import, job or request row. (self-review: `key-provenance`)
- **The check before the work covers the whole quantity.** Check N units when the work will charge N, not 1, and a fallback debit of the application's ledger refuses or clamps; it never takes a balance below zero. The check runs before anything that costs money, a paid provider call included. (self-review: `check-quantity`)
- **Each service settles its own pending units.** Every job queue or table for Nozle work has a name unique to the service, so services that share a Redis or database never take each other's jobs. (self-review: `pending-owner`)
- **A missed customer lookup is not cached.** Cache a resolved customer, never a miss: a company created a moment ago must be billed and allowed on its next request. (self-review: `seed-before-read`)
- **Every recorded decision is in the code.** For each entry in `decisions` that changes behavior, the report names the file and line that implements it; a decision without code is a scope change to raise with the user.
- **Going back is safe.** Switching from enforce back to shadow or off must not strand credits in Nozle that the app can no longer spend: either keep reading the Nozle balance for companies that were enforced, or move their remaining balance back with a recorded, idempotent step. Say which in the scope.
- **One mode for every service.** Every service that sends usage or cost events, or gates on Nozle, reads the same off, shadow and enforce setting; off sends nothing from any service. Show with a test or a code trace that off mode makes no new table reads or writes and needs no new column or table. (self-review: `off-mode`)
- **No per-unit request fan-out.** A request that would make one credit call per item in a loop moves to a background job, or uses a quantity-valued meter where the account has one. Usage events for many items go in one batch call, or through the SDK's event buffer for high volume from many requests (`/sdks/<lang>/tracking-events`).
- **An event buffer is not a durable store.** Use it for high-volume usage events where a few events lost to a killed process are acceptable, never for credit spends or for an answer the code acts on. Pass the business transaction id on every buffered event, wire its error callback to the app's logs or a pending store and handle every error kind the SDK page lists, and flush or close it before a serverless handler returns and on shutdown. Where the user needs every event, store the event before sending and settle from that store instead. (self-review: `pending-owner`)
- **Spend caps are money, usage limits are units, credits are a balance.** Each refuses with its own reason; each is a product refusal (see "Refusals and errors"). Usage events are never refused by a cap, because the usage already happened: the cap is enforced where the code checks before the work. A plain check before a call can be overrun by calls in flight; when the user needs an exact cap under concurrency, hold first. Say in the scope which one the user chose. (self-review: `charge-order`)
- **A credit hold is settled on every path.** Every hold is finalized with the actual usage on success and released on failure, cancel, timeout or an exception (a `finally` or a deferred release), and a worker that may crash relies on a TTL just above its longest run. The create key comes from the unit and never uses a prefix the docs reserve; the timestamp is fixed and stored with the unit for create and for finalize. A hold is not a charge: the finalize replaces the credit call for that work (never both). (self-review: `charge-order`)
- **Read only fields that exist.** Read a response field only when the installed SDK's types or the docs' response example declare it. When a needed field is missing, use the documented REST read or list it as a gap.
- **Mock Nozle at the HTTP boundary, not the client.** A test fakes `fetch` or the HTTP layer (or the SDK's transport), not the app's whole Nozle client, and asserts the method, the full URL (service host and path, from the API reference) and the body of every call. A fake that replaced the client passed every phase test while one call went to the wrong service.
- **Every plan the app has is mapped from its data.** Read the plan names and codes from the app's seeders, migrations and price book, and map each one. A plan with no mapping is reported, never skipped. (self-review: `nullable-fields`)
- **A path that cannot run says so.** When enforce cannot start for a customer (no customer or subscription yet, no mapping, no balance moved), log it once with the reason and show it in a status or readiness read; never fall back to off silently. (self-review: `shadow-seed`)
- **Tests drive the money paths.** A call site that moves money is not `completed` without a test that drives it, and the charge path is tested once against a real database or the ORM's real query layer, not only a fake spender. Fakes go through a store seam or a real database, never by matching SQL text; the status reader is tested against the installed SDK's real error shape.
- **Fail open or fail closed is decided by one question:** does the work go ahead without a confirmed charge? Label it from the code path, never from intent.

## Found in live tests against a real account

Each rule below comes from an integration whose unit tests passed while the same flow failed against a live Nozle organization. Each has a self-review check (in brackets). Most of these bugs were in existing application code the integration read (how the app writes periods, ids and domains), so check the producer, not only the new code.

- **Resolve the customer from a stored id, never from a derived value** (`identity-lookup`). When the code finds the Nozle customer through a value rebuilt from another one (a domain rebuilt from a schema or tenant name, a slug turned back into a name), check that the conversion is exactly reversible for every allowed input: a lossy one (`-` and `.` both stored as `_`) silently skips billing for some customers. Look the customer up by a stored primary key or the stored external id instead. The self-review evidence names the lookup and why it cannot miss.
- **Every existing gate on a moved path reads the new source** (`legacy-gates`). Before scope approval, list every existing balance, credit, quota or plan check (middleware, route guard, controller check, frontend gate) on each path whose charging moves to Nozle. After cutover each one either reads Nozle or is removed in the same step: a gate still reading the drained legacy balance refuses users who have Nozle credits. List them in the scope, and test each metered path in enforce for a customer whose only credits are in Nozle (the legacy balance at zero): no gate may refuse it. Find the gates by searching the code for every read of the legacy balance (middleware, controllers, services, other repositories), not only the routes the study named. A gate and a display read the same balance the charge spends, including credits bought through the legacy provider when the fallback spends them.
- **Every plan and every nullable field is handled** (`nullable-fields`). Read the real model, migrations and seed data for the records the integration reads (subscriptions, plans, periods, companies), not only the code that writes them. Note each field that can be null for some plans (a free plan with no period dates) and handle it: a cutover or enforce path that needs a period must say what it does for a plan without one. Tests cover every plan the app has, including the free one.
- **One clock per period** (`one-clock`). Compute a period's start and end from one timestamp taken once (`end = addPeriod(start)`), never from two separate reads of the clock: a 1 ms difference fails Nozle's cadence check and leaves the subscription stuck.
- **A retry after a denial needs a new attempt** (`denial-retry`). Nozle replays the stored answer for a transaction id it has seen, denials included, so a unit denied at zero balance stays denied under the same key after credits are added. Keep the business id as the key's base and add an attempt number that changes only after a recorded denial (stored with the unit), so a network retry reuses the key and a retry after a denial does not. Do not stop a whole batch at the first denial when the units are independent. A recorded denial or debt has a collector: when credits arrive by any path the app supports (renewal, top-up, purchase, plan change), a job or the credit-arrival handler retries or charges it. A debt nothing reads is forgiven, so say in the scope which one the user chose.
- **Mark a webhook or order handled only after it is fulfilled** (`claim-after-fulfil`). Set the "processed" marker in the same transaction as the fulfilment, or make the fulfilment safe to run again; a marker set before a fulfilment that then fails makes every provider retry skip the work.
- **The status reader is tested on the real error** (`status-reader`). The code that turns an SDK or HTTP error into a status is tested with the exact error the installed SDK throws (read its source or capture one), for 401, 402, 404, 409 (each 409 code the call can return), 422 and a network error. A reader that misses a format treats every error as retryable and fails open.
- **Every meter, feature and plan code exists in the account** (`codes-exist`). Each code the integration sends (event codes, feature codes, plan codes, credit system codes) is one the account read showed, in a usable state (a plan the account read lists as archived is refused for new subscriptions and checkout), and each account object a call depends on exists too (for example a credit pool policy before credits are spent per entity, or a meter that sums a quantity when an action charges one), or a dashboard step in `nozle-setup-plan.yaml` creates it before that path is enabled. Read the call's page for the objects it needs.
- **Every new runtime dependency is a setup step.** A queue, cache, cron, worker process or table the integration adds (for example a Redis-backed queue) is listed in the setup plan with what it needs to run, and the code says what happens when it is missing; an operator must never find it from a failure.
- **Changed files pass the project's lint and type check** (`lint-clean`). Run the project's linter and type checker on the changed files (`nozle-verify`), and fix every new error; an undefined variable in an error branch crashes exactly the path that tests skip. When they cannot run, the check is `fail` with the reason, never `pass`.
- **What is charged stays what was charged** (`charge-parity`). Before scope approval, show a table of every outcome on each billed path (success, empty result, no match, duplicate, provider failure) with what the app charges today and what it will charge after. Any difference is a decision for the user, never a side effect of the build.
- **Shadow mode has something to compare** (`shadow-seed`). Shadow mode creates the Nozle customer and its subscription before it compares, so the comparison runs against real data; a shadow mode that compares against a customer that does not exist yet only logs 404s.
- **A dedupe record is scoped and unique** (`dedupe-scope`). An app-side record that remembers a key (a request id, an idempotency key, a unit id) is looked up by the customer and the action as well as the key, and the database enforces it with a unique index on those columns, so a second company's request never returns the first company's result and two concurrent requests with one key create one record (insert first, then charge; a conflict means replay). Test it with two companies and with parallel requests (at least three at once with one key): the app's own ledger must move once as well as Nozle.
- **Every route that spends is in the charge table** (`route-coverage`). Find spend paths by listing the routes and jobs that change a balance or call a paid provider (routers, controllers, workers, deprecated controllers still mounted), not only the services the study named. Each one appears in the charge-parity table and is either metered or explicitly excluded by the user; a still-mounted legacy route that only checks the legacy balance blocks users after cutover.
- **Seed before the first read** (`seed-before-read`). The first call for a new customer waits for the customer and subscription to exist (await the mirror, or retry the read once it completes); a fire-and-forget mirror followed by an immediate read loses that call.
- **Know what happens at period end before writing renewal code** (`next-period`). Nozle renews a paid subscription and issues the new period's grant by itself once the renewal is paid; an unpaid renewal moves it through dunning, and the app's access follows that state from webhooks and reads, never from its own clock alone. Before creating anything at renewal, read the customer's subscriptions: the renewed one is the same subscription, so never create a second active one (every `nozle.usage.track()` then fails with 422 `active_subscription_ambiguous`). The renewed grant can appear before the subscription's own period fields move, so decide that Nozle renewed from the customer's credit grant for the new period, not from the period dates. When the app's own renewal code also grants credits, it must stop doing so for customers whose allowance is in Nozle (that doubles the allowance). Test it by moving the period end into the past in a fake that answers as Nozle does: one active subscription, the allowance counted once, and the app's gate following the new state.
- **Cost events carry the id of the provider call** (`cost-event-id`). One real provider call gets one id, taken from that call (the provider's request id, or the job, item and attempt that made it) and scoped to the customer; a retry of the same call reuses it. Never a random id per send, and never a content hash or a day bucket: two customers fetching the same content, or two real calls on one day, are separate costs. A retry sends the same body, timestamp included, so store the timestamp with the id. A cost event goes out after the call it costs, never before its charge. `parent_transaction_id` must be the transaction id of a usage event that was actually sent (the same string, built the same way); when there is none, send the cost with `external_customer_id` and no parent. A parent id that names anything else (a data row, the provider call id) leaves the cost `pending_parent`, never rated.
- **A track-time denial has a defined outcome** (`denial-after-work`). When the work ran and `nozle.usage.track()` is then denied, the code follows the charge-order decision the user made (charge the legacy balance, record a debt, or block the next action); it never lets the work go uncharged silently.
- **A limit display reads what actually limits** (`limit-source`). For a credit-backed feature, `nozle.can()` keeps answering allowed at zero balance (the limit is the credit balance), so a "used up" or upgrade notice reads the balance or `nozle.usage.check()`; for a feature with a usage cap or a boolean entitlement, it reads `nozle.can()`. Test the display at zero balance and at the cap.
- **A call between services matches the provider's route exactly** (`peer-contract`). When one service calls another to charge or check (a relay to the service that holds the key), the client's base URL, path prefix, method, headers (including any `Idempotency-Key` the provider requires) and body match the provider's route definition. Test the client against the provider's real router (start it locally, or import the router), not only against a mock written from the client's side. The evidence names the provider route line and the client call line.
- **A fake refuses what the real API refuses** (`fake-refusals`). A test fake answers each call the way the API reference says the real service answers it in that state, refusals included: the documented status and code for a call the docs exclude (a cancel or plan change on a subscription billed outside Nozle, an event with no or several active subscriptions, a period that does not contain the current time, a reused key with a new body), not a success. Before writing any Nozle call, read in the API reference whether it is allowed for that customer's billing state; for each call the code makes, the test suite has one case where the fake returns the documented refusal and the code handles it. A fake that accepts every call cannot fail, and in live tests it hid calls that Nozle refused every time.
- **One failing step never blocks the others** (`step-isolation`). A sync, mirror, reconcile or settle job saves each step's result as soon as that step succeeds, and a failing remote call records its error with the item and is retried later; it never throws past the save of steps that already succeeded, never stops the job for other customers, and never leaves stored state behind what the remote side already holds. Test it with the fake failing one call in the middle and check that the earlier steps are saved and the next customer is processed.

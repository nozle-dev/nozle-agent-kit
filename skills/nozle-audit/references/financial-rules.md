# Financial and runtime integration rules

Use current product docs, account configuration, Core and Engine contracts, and supported SDKs to validate each proposed integration.

- Derive the Nozle customer and organization from authenticated backend identity; keep runtime secret keys server-side.
- Select the subscription explicitly when more than one can be active. Surface ambiguity.
- Preserve both transaction ID and timestamp across retries; prevent duplicate billing for a single consumption.
- `can()` is a check, not a credit reservation. Use a verified atomic usage path for consumption when required.
- LLM wrappers can emit feature usage plus optional cost events. Inspect shared clients, including free callers, before wrapping. For cost-only integration, use direct approved cost tracking.
- Treat plan grants and purchased top-ups as distinct credit sources. Preserve decimal precision, expiry, rollover, and consumption rules.
- Entity allocation may reserve credit balances. It does not prove support for an unreserved per-member cap on a shared company pool.
- Fulfill checkout only after authoritative payment confirmation. Verify webhook signatures and process deliveries idempotently.
- New cost configuration uses Cost Sheets. Respect cost composition to avoid double counting. Unknown rates remain uncosted and cost processing may be asynchronous.
- Fixed top-up package support does not establish arbitrary-quantity top-ups. State this as a gap when the app requires a slider model.
- Use the installed SDK interfaces and Engine contracts. Core OpenAPI omits several Engine routes. The published Node package is `@nozle-js/node`; the React package is `@nozle-js/react`; Python is `nozle-sdk`.

## Credentials stay with the user

- Never create, request, paste, read, or store a Nozle API key, and never write a key value to any file. The user makes keys in the dashboard. To confirm the user's keys work, run `nozle-check key <app directory>` (or `node <skill folder>/scripts/nozle-check.mjs key <app directory>`) as one plain command: it reads the keys from the environment, `.env.local` or `.env` itself, asks Nozle's plan catalog (read-only, nothing billable), and prints only each variable name, its source and the verdict, never the value. Run it when the user says the keys are in place, and report the verdict: a rejected key goes back to the user's steps.
- Add every variable the new code needs to `.env.example` with an empty value and a one-line comment (for example `NOZLE_API_KEY=` for the server-side secret key, and a separate publishable-key variable only if client code needs one). Read them from the environment in code, and make the code fail with a clear message when one is unset. Leave `.env` and other real env files untouched.
- End the hand-off with the dashboard steps the user must do themselves, in order, before the integration works: create the API key(s) in the Nozle dashboard under **Settings > API Keys**, copy them into their own `.env`, plus each missing account setup item from the coverage map (plans, meters, provider connection, webhook endpoint, and the like). List a step only when this app needs it.
- Offer the first-event check as the last user step. The user runs `node <installed skill folder>/scripts/nozle-first-event.mjs --customer <id> --event <meter code> --subscription <id>` (dry run by default; `--yes` sends one real, billable event using `NOZLE_SECRET_KEY` from their own shell). The agent never runs it: the guard hooks deny any command that names it.
- Amounts from Nozle are minor units. Convert them for display only, never for totals, and give the currency's decimal digits a fallback (for example `formatter.resolvedOptions().maximumFractionDigits ?? 2`) so strict TypeScript compiles. Two earlier runs failed `tsc` and `astro check` on exactly this.
- Give each unit one fixed timestamp (the business event time, or the one stored when the unit was first attempted) and reuse it with the same idempotency key on every retry. The SDK stamps the current time when none is passed, so a retry becomes a different payload and returns 409. An identical payload replays to the original result, a denial included; a 409 is a caller bug, never proof that the unit was charged.
- If the application keeps its own balance next to Nozle, make that deduction idempotent too: record the transaction id with a unique key in the same database transaction as the deduction, and decrement atomically (in SQL, under a row lock) rather than read, subtract and save. Nozle's key protects only Nozle's side.
- Keeping an existing payment provider with Nozle metering (external billing authority): import each subscription and its opening balance together, once per subscription with a stable external reference, for every subscription and not only in a one-off cutover; never import a new subscription per period, because the Engine renews the grants by itself after the opening import and a second active subscription makes `usage.track` fail with 422 `active_subscription_ambiguous` (it has no subscription field); Nozle cannot cancel or change an externally billed subscription and keeps renewing its grants, so the application checks its own paid status before every usage call and stays the authority for cancellation and plan changes.
- Create plan entitlements with PATCH; POST replaces every existing entitlement of the plan.


## Build traps seen in testing

- **Usage keys come from a business or request id.** Build the idempotency key and transaction id from something that stays the same on every retry: the job and item id, a client-supplied message id, the provider's response id, the inbound request id, or the payment or order id. Never generate it per attempt (`randomUUID()`, `uuid4()`, `nanoid()`, `Date.now()`). When no stable id exists, create one when the unit is first stored and reuse it. Check a 409 by its status code and log it as a caller bug. Where the status lives: the REST response status; Python `NozleAPIError.status_code`; the Node SDK rejects with a plain `Error` whose message contains the operation and the HTTP status (no documented status field), so read the number from that message in one helper that matches the status exactly as the SDK writes it (check the installed SDK source or an error it produced), never any three digits in the text (a port, an address or a duration would pass for a status), or call REST where the decision matters. Never decide by searching the message for words such as "duplicate" or "already".
- **A client-supplied id is not a billing key by itself.** When the key comes from an id the client sends (a message or request id), the server must also dedupe the work: store the id with a unique constraint and return the stored result for a repeat, without a new provider call. Otherwise a client that reuses one id gets unlimited free work while Nozle dedupes the charge. Without that store, use a server-made id saved with the unit.
- **Streams are billed on provider finish.** Record usage when the provider reports final usage, whether or not the client is still connected, and record it before writing the final chunk to the client. An abort after the provider finished is billed; an abort before it is not. Do not pass the client's abort signal to the provider call: when the client disconnects, keep reading the provider stream to its final usage, then bill (or stop the provider explicitly and bill the usage it reports, when the user chose that).
- **Use the subscription id that exists.** The code may choose a deterministic external id when it creates the subscription (for example `sub_${userId}`), but when the lookup finds an existing one (made in the dashboard or by another path), store and use that subscription's id; never rebuild the id and assume it matches. When the customer has exactly one active subscription, omitting it lets the SDK resolve it.
- **No paid subscription without payment.** Subscribe a customer to a paid plan only after checkout or confirmed payment. One code path owns subscription creation: look up the active subscription first, then create. A free plan is assigned once, at signup.
- **Replacing an existing app balance needs a rollout.** When the application already holds balances or quotas, the scope must have off, shadow and enforce modes and a plan for every existing balance before enforce. The opening-balance import (`POST /customers/{id}/credit-balance-imports`, Engine, dry run first) exists only for an externally billed subscription, after its billing-state import, and `remaining_amount` cannot exceed that period's plan grant. Purchased credits and balances under Nozle billing have no import and there is no manual grant route, so propose a drain and let the user choose: spend the legacy app balance first and move each user to Nozle when it reaches zero, or keep honoring it beside Nozle until it is spent; never strand it. Schema and model changes must work before their migration runs (a nullable column, code that reads both shapes), so `off` really changes nothing for current users. Off and shadow never create customers or subscriptions and never change an account; shadow only reads (`can()`, `usage.check`) and logs, unless the user chose a shadow that also sends usage. Ship the migration file with every schema change (Prisma, Alembic, Rails, SQL); a model change without its migration breaks the app at deploy.
- **An import covers one period, so the scope needs the renewal path.** The billing-state import mirrors the current period only. The scope must include what imports the next period when the application's own provider confirms the next payment, and what happens to a company whose period has ended without one (the app's own paid-status check decides, and Nozle's `usage.track` will 4xx after `period_end`). A cutover script that reuses its saved state on a re-run never imports a new period; say so and plan the renewal trigger. A cancelled or unpaid company must not keep spending a Nozle balance: check the app's paid status before each usage call.
- **External billing renewal and restart.** Before importing billing state again, look up the existing import, or replay it with the original body and key. Never reuse one idempotency key with a new body.
- **An uncertain charge stays pending, never failed.** After a timeout, a network error or a 503 the charge may have landed. Keep the unit `pending` with its key and settle it later with the same key and body; a retry by the user resumes that pending unit instead of creating a new one with a new key, which would charge twice.
- **A legacy remainder smaller than one unit is never stranded.** One unit cannot be split across the legacy balance and Nozle, so ask the user and record the choice: let the legacy balance pay the whole unit while any of it remains (set it to zero; generous, drains fully), or show the remainder and refund or convert it. Never silently charge the full unit in Nozle while the remainder sits unspent.
- **Charge order for work that can fail is a user decision.** Nozle has no usage reversal or reservation, so ask which one the user wants and write it in the scope: (a) charge first with `usage.track` and run the work only when `allowed` is true; a failed job stays charged unless the app compensates in its own records; or (b) `usage.check` before (advisory), the work, then `usage.track` with a key from the job id after success; concurrent requests can overspend, and when that `usage.track` returns `allowed: false` the app must record the debt and deny the next request instead of only logging it. Never treat a denial as a log line.
- **Errors decide behavior by type.** Fail open (let the action through) only on a network error, a timeout or a 5xx, and only when the user chose fail-open; an authentication error, a 4xx or a missing subscription is a configuration problem, so deny or surface it and never swallow it with a catch-all. Retry only a network error, a 5xx or a 503 (after `Retry-After`) with the same key; never retry a 4xx. A unit that fails permanently (a 4xx) is marked failed for review and logged; it never blocks that user's later requests. A loop that settles stored units before new work catches each unit's error on its own, marks a permanent failure, and continues; only a transport error or 5xx may stop it, and even then the new request follows the chosen outage rule, not the stuck unit. Python: `NozleTransportError` and 5xx `NozleAPIError` are retryable; `NozleAuthenticationError` and other 4xx are not. Node 0.10.0 and Python 0.10.0 expose the API error code: `NozleApiError` (`status`, `code`, `hasCode()`) on Node `checkout`, `checkoutStatus`, `verifyCheckout`, `checkoutInvoice` and margin calls, `NozleAPIError.code` and `has_code()` on Python; match the code, not the message. Node `track`, `usage.track`, `can` and `credits` still throw a plain `Error` with the status only in the message, so read the status from the failed response where the code owns the call or wrap it once.
- **Async servers.** The Python SDK is synchronous: call it through `asyncio.to_thread` or `run_in_threadpool` from `async def` routes.
- **Keys that stay unique.** An autoincrement row id repeats across environments and database resets; prefix the key with the environment or use a UUID column created with the row.
- **Python SDK.** Published `nozle-sdk` (0.9.1 and 0.10.0) has `usage.track(..., timestamp=)` (a fixed per-unit timestamp is possible) and `cost_events.track(...)` (Engine host, `timestamp` as a float of Unix seconds); the Python docs do not list either, so check the installed package. `usage.check` names its time parameter `occurred_at`. The client is synchronous (`requests`), zero-retry, and has no batch, import or webhook-verification method.
- **Cost events host.** `POST /api/v1/cost-events` is served by Engine in the code. The published OpenAPI lists it under Core; call Engine and say the docs disagree.
- **A money move between two ledgers happens once, enforced by the database.** An import, renewal or opening balance that debits the application's own ledger must, inside the debit transaction, insert a unique claim row keyed by the customer and the period (or re-check the state under a row lock), and compute the amount from rows locked in that same transaction. An amount read before the transaction and used inside it lets two concurrent callers debit twice. (self-review: `ledger-once`)
- **Every pending or uncertain charge has an owner that runs without user traffic.** A job, queue or scheduled task settles pending units with their stored key and timestamp. Settling only inside a request path (for example only when the wallet runs short) leaves work unpaid when the customer makes no further request; say who settles a pending unit if this customer never calls again. (self-review: `pending-owner`)
- **Never call Nozle inside a database transaction that can still roll back.** Charge after the commit, keyed by the committed record. A charge inside the transaction survives a rollback (an overcharge), and an HTTP call inside it holds row locks for its whole timeout. (self-review: `charge-in-transaction`)
- **A key comes from one stored business record whose existence is the billable event.** Ask: can a new billable event ever produce this key again? A hash of content that can recur (the same lead list imported again after a delete, the same prompt text) can, so it is refused; use the id of the stored import, job or request row. (self-review: `key-provenance`)
- **The check before the work covers the whole quantity.** Check N units when the work will charge N, not 1, and a fallback debit of the application's ledger refuses or clamps; it never takes a balance below zero. (self-review: `check-quantity`)
- **Off mode is proven unchanged, not asserted.** Show with a test or a code trace that off mode makes no new table reads or writes and needs no new column or table. Anything else is a behavior change the user approves in the scope. (self-review: `off-mode`)
- **External billing renewal is part of the build.** When the product keeps its payment provider, the scope includes what imports the next period. If it is not built, the enforce gate itself refuses once the current time is past the imported period end, and the record says enforce is not ready; a flag and a note are not enough. (self-review: `renewal`)
- **No per-unit request fan-out.** A request that would call `usage.track` once per credit or per item in a loop (hundreds of sequential calls) moves to a background job, or uses a quantity-valued meter where the account has one; one request never waits on hundreds of Nozle calls.
- **Tests drive the money paths.** A call site that moves money is not `completed` without a test that drives it. Fakes go through a store seam or a real database, never by matching SQL text; the status reader is tested against the installed SDK's real error shape (for example a plain `Error` with `"<operation> failed: <status> <text>"`).
- **Fail open or fail closed is decided by one question:** does the work go ahead without a confirmed charge? Label it from the code path, never from intent.

## Found in live tests against a real account

Each rule below comes from an integration whose unit tests passed while the same flow failed against a live Nozle organization. Each has a self-review check (in brackets). Most of these bugs were in existing application code the integration read (how the app writes periods, ids and domains), so check the producer, not only the new code.

- **Resolve the customer from a stored id, never from a derived value** (`identity-lookup`). When the code finds the Nozle customer through a value rebuilt from another one (a domain rebuilt from a schema or tenant name, a slug turned back into a name), check that the conversion is exactly reversible for every allowed input: a lossy one (`-` and `.` both stored as `_`) silently skips billing for some customers. Look the customer up by a stored primary key or the stored external id instead. The self-review evidence names the lookup and why it cannot miss.
- **Every existing gate on a moved path reads the new source** (`legacy-gates`). Before scope approval, list every existing balance, credit, quota or plan check (middleware, route guard, controller check, frontend gate) on each path whose charging moves to Nozle. After cutover each one either reads Nozle or is removed in the same step: a gate still reading the drained legacy balance refuses users who have Nozle credits. List them in the scope.
- **Every plan and every nullable field is handled** (`nullable-fields`). Read the real model, migrations and seed data for the records the integration reads (subscriptions, plans, periods, companies), not only the code that writes them. Note each field that can be null for some plans (a free plan with no period dates) and handle it: a cutover or enforce path that needs a period must say what it does for a plan without one. Tests cover every plan the app has, including the free one.
- **One clock per period** (`one-clock`). Compute a period's start and end from one timestamp taken once (`end = addPeriod(start)`), never from two separate reads of the clock: a 1 ms difference fails Nozle's cadence check and leaves the subscription stuck.
- **A retry after a denial needs a new attempt** (`denial-retry`). Nozle replays the stored answer for a transaction id it has seen, denials included, so a unit denied at zero balance stays denied under the same key after credits are added. Keep the business id as the key's base and add an attempt number that changes only after a recorded denial (stored with the unit), so a network retry reuses the key and a retry after a denial does not. Do not stop a whole batch at the first denial when the units are independent.
- **Mark a webhook or order handled only after it is fulfilled** (`claim-after-fulfil`). Set the "processed" marker in the same transaction as the fulfilment, or make the fulfilment safe to run again; a marker set before a fulfilment that then fails makes every provider retry skip the work.
- **The status reader is tested on the real error** (`status-reader`). The code that turns an SDK or HTTP error into a status is tested with the exact error the installed SDK throws (read its source or capture one), for 401, 404, 409, 422 and a network error. A reader that misses a format treats every error as retryable and fails open.
- **Every meter, feature and plan code exists in the account** (`codes-exist`). Each code the integration sends (event codes, feature codes, plan codes, credit system codes) is one the account read showed, or a dashboard step in `nozle-setup-plan.yaml` creates it before that path is enabled. A missing meter returns 404 on every call.
- **Changed files pass the project's lint and type check** (`lint-clean`). Run the project's linter and type checker on the changed files (`nozle-verify`), and fix every new error; an undefined variable in an error branch crashes exactly the path that tests skip. When they cannot run, the check is `fail` with the reason, never `pass`.
- **What is charged stays what was charged** (`charge-parity`). Before scope approval, show a table of every outcome on each billed path (success, empty result, no match, duplicate, provider failure) with what the app charges today and what it will charge after. Any difference is a decision for the user, never a side effect of the build.
- **Shadow mode has something to compare** (`shadow-seed`). Shadow mode creates the Nozle customer and its subscription (or imports billing state) before it compares, so the comparison runs against real data; a shadow mode that compares against a customer that does not exist yet only logs 404s.
- **A dedupe record is scoped and unique** (`dedupe-scope`). An app-side record that remembers a key (a request id, an idempotency key, a unit id) is looked up by the customer and the action as well as the key, and the database enforces it with a unique index on those columns, so a second company's request never returns the first company's result and two concurrent requests with one key create one record (insert first, then charge; a conflict means replay). Test it with two companies and with parallel requests.
- **Every route that spends is in the charge table** (`route-coverage`). Find spend paths by listing the routes and jobs that change a balance or call a paid provider (routers, controllers, workers, deprecated controllers still mounted), not only the services the study named. Each one appears in the charge-parity table and is either metered or explicitly excluded by the user; a still-mounted legacy route that only checks the legacy balance blocks users after cutover.
- **Seed before the first read** (`seed-before-read`). The first call for a new customer waits for the customer, subscription and opening balance to exist (await the mirror, or retry the read once it completes); a fire-and-forget mirror followed by an immediate read loses that call.
- **Know what happens at period end before writing renewal code** (`next-period`). In a live test, Nozle renewed an imported external subscription's period and grant on its own after the period ended, and a second import under a new reference created a second active subscription, after which every `usage.check` returned 422 `active_subscription_ambiguous` and the customer was locked out. Before importing anything at renewal, read the customer's subscriptions: when the existing one is active for the new period, only reconcile (do not import, do not grant again); import only when none is active, under the original reference. Never create a second active subscription for one customer. In the same test the renewed grant appeared before the subscription's own period fields moved, so decide that Nozle renewed from `usage.check` succeeding (or the new grant), not from the subscription's period dates. When the app's own renewal also grants credits, the app must not grant them again for a customer whose allowance now lives in Nozle (that doubles the allowance). Test it by moving the period end into the past and checking that the customer still has exactly one active subscription, enforce resumes, and the allowance is counted once.
- **Cost events carry the id of the provider call** (`cost-event-id`). One real provider call gets one id, taken from that call (the provider's request id, or the job, item and attempt that made it) and scoped to the customer; a retry of the same call reuses it. Never a random id per send, and never a content hash or a day bucket: two customers fetching the same content, or two real calls on one day, are separate costs.
- **A track-time denial has a defined outcome** (`denial-after-work`). When the work ran and `usage.track` is then denied, the code follows the charge-order decision the user made (charge the legacy balance, record a debt, or block the next action); it never lets the work go uncharged silently.
- **A limit display reads what actually limits** (`limit-source`). For a credit-backed feature, `can()` keeps answering allowed at zero balance (the limit is the credit balance), so a "used up" or upgrade notice reads the balance or `usage.check`; for a feature with a usage cap or a boolean entitlement, it reads `can()`. Test the display at zero balance and at the cap.

# Integrate Nozle into an application

Use the host coding agent's repository tools for analysis and implementation. Use the Nozle documentation MCP for product behavior and the OAuth account MCP for the selected merchant's configuration. Supporting details are in [capability-menu.md](references/capability-menu.md), [financial-rules.md](references/financial-rules.md), [runtime-contracts.md](references/runtime-contracts.md), [api-map.md](references/api-map.md), [stack-support.md](references/stack-support.md), [record-format.md](references/record-format.md), [connect-and-read.md](references/connect-and-read.md), and [inspect-stack.md](references/inspect-stack.md), [plan-design.md](references/plan-design.md), and [prerequisites.md](references/prerequisites.md), and [decision-questions.md](references/decision-questions.md), and [asking.md](references/asking.md). Some hosts deny separate reads of installed plugin references; use the binding menu and rules in this file for the first response. Read references with the host's file-read tool, never `cat` through the shell, and run every shell command on its own: no `cd … &&`, `&&`, `||`, `;` or pipes into another command, because hosts that run without an approver refuse chained commands. Never ask the user to paste plugin reference files. Before contract-specific code, obtain current documentation through the docs MCP or another authorized docs read; if unavailable, mark the contract unverified and defer dependent edits.

## Stay in this skill for integration work

This skill adds or improves Nozle functionality. Sibling skills handle other intents: `nozle-audit` finds opportunities and gaps with no edits, `nozle-doctor` checks an existing implementation, `nozle-resume` continues approved work from a saved record, and `nozle-setup` connects the account and finishes dashboard setup. A question about how Nozle works is answered from the docs without a repository scan.

If the user named an outcome, retain it. A read-only evaluation of an integration request stays in this skill for planning; it only forbids edits. Check the stack first (step 1), then connect the account and scan the codebase before the menu. The first integration response gives the stack-support statement from [stack-support.md](references/stack-support.md) (stack, backend path, frontend path, and plainly "There is no Nozle SDK for <framework>" when that is true). Never write that SDK support is unverified: run `nozle-check env` for the verdict and read the docs MCP SDK list; `@nozle-js/node` covers a Node or TypeScript backend, `nozle-sdk` Python, `@nozle-js/react` React, a **Linked services** line (required whenever the code calls a service that is not in the folder, even when other services of the product are present: list each external host or base-URL variable with its apparent role, and ask where it lives, or say none were found), two to four lines on what the product does and where billing, usage, or AI calls happen, an **LLM capture** line per service whenever the code holds an LLM client (provider and language, and whether automatic capture applies; when it does not, say plainly that everything can still be tracked by reporting the provider's returned token usage and Cost Events from the backend, as in capability 7), then only the choices below that make sense for this product, judged from the code and account evidence, each with its exact label and its original number (the numbers stay stable so a user can refer to a hidden one). Leave a choice out only when the evidence shows it does not apply here (a missing backend or frontend is a requirement to state, not a reason to hide it), and say in one line which were left out and why; when evidence is thin, show it. Put one finding line under each shown choice: this account's status from `get_capability_catalog` (ready, needs setup, unknown), where it would plug into this code, and whether it fits (recommended or optional; a choice that is not applicable goes in the left-out line, not the list). Add an end-to-end line: which parts the choice needs (backend for secret-key calls, webhooks, and usage events; frontend for pricing, checkout, and billing screens), which of them this project already has, and which are missing. When a needed half is missing (for example a static site with no server for a choice that needs one), say so plainly and name the options: add a backend in this project, use a separate service the user owns, or keep the choice out of scope. Do not leave out a choice only because a half is missing; show it with that requirement. Mark any inferred selections, and allow multiple selections or a custom goal. List problems the code study found (security, races, wrong status codes) as findings with an optional fix; promise a fix only when it is in the approved scope. End that response with the next user decision needed; after the repository and account review, request explicit approval of the concrete scope before any edit. A user request to move quickly does not remove this menu or authorize billing assumptions.

## Ask with the host's question tool

Every choice or approval (goals, business decisions, what to measure, provider, scope) goes through the host's structured question tool, so the user picks from a list with a keypress. Details, tool names and an example: [asking.md](references/asking.md). In Claude Code the tool is `AskUserQuestion`; in Codex CLI `request_user_input` (interactive sessions only); in OpenCode `question`; other hosts: the tool in your list that shows options and returns the choice.

- **Tool first, text only as the fallback.** Never print the questions as a typed list and wait when the tool is available. Fall back to a short numbered list (recommendation first) only when the tool is not in your list, returns "not supported" (headless or `exec` runs) or is denied.
- Put the findings, the menu and the plan in your message first. The tool shows only the questions, so each question must stand alone and name the concrete thing it is about (the endpoint, the amount, the plan).
- One call holds up to four related questions. Each has two to four options. Put your recommendation first and end its label with "(Recommended)". Each option's description says what it means for charges or for current users. The user can always type another answer under "Other".
- Goals: every choice you show is selectable. Split them over up to four multi-select questions in one call, grouped by theme, each label starting with the choice's original number; left-out choices stay available by typing their number.
- Decisions that change charges, exclusions or payer: one question each, never a guess, and never a default the user did not see.
- Scope approval: options such as "Approve the whole scope (Recommended)", "Approve selected phases", and "Change the scope". The user approves only what they have read, so the scope is always in your message first.

## One capability, or a later addition, still means the whole chain

The user may ask for a single thing ("integrate credits", "add usage tracking") or come back later to add one. Either way the flow does not shrink: no capability works alone.

- A direct request for one capability runs every step below (stack check, connect, read the account, study the code). The first response says what the capability stands on, using [prerequisites.md](references/prerequisites.md): the base (server, key variable, payer identity, Nozle customer, onboarded organization) plus that capability's own chain (for credits: credit system and rates, a grant rule or package, consumable meters, exactly one active subscription, the spend paths on `usage.track`). Each row is marked present, missing or unknown, with its evidence from the account read or the code.
- The scope lists every missing dependency as its own step, ordered with `depends_on`, and the user approves the whole set, not only the item they named. Missing account items become dashboard steps; code that needs them waits until a fresh read shows them. A dependency that cannot be met (no server, an unsupported provider, something the account cannot model) is stated plainly with the options; the dependent part is not built.
- A choice left out of the first menu can be asked for at any time. Treat it exactly like a direct request.
- When `nozle.integration.yaml` already exists, read it first. Its goals, approved scope, decisions and `stack` are the baseline. Re-read the account and recheck the scoped files for drift (as `nozle-resume` does), add the new goal to `selected_goals`, show only the new steps as a delta, and get approval before editing. Never redo or redesign approved items; a change to one needs the user's yes. Use `nozle-audit` to look for further opportunities and `nozle-doctor` to check what was built.

## Works without a login, and continues after it

The code study never waits for the account. Everything the code can tell (stack, what is already in place, every activity that spends or consumes something, identity, linked services, defects) is done and shown whether or not the account tools are connected.

- **No login yet:** do steps 1 and 4 in full, then write `nozle-study.yaml` (below) to the repository root with the file-write tool and validate it with `nozle-check nozle-study.yaml` BEFORE you answer (writing it is not editing application code; the "no edits" rule does not cover it), end the answer with the line `Saved: nozle-study.yaml`, and show the result as **Findings from the code (account not read yet)**: the activity table with each activity `unknown` against the account, the already-in-place table, the defects, and what would need to exist in the dashboard (as suggestions, not facts). Then say in one line how to log in on this host (see [connect-and-read.md](references/connect-and-read.md)) and ask with the question tool: log in now, continue docs-only, or stop here. Never present docs as the user's account, and never stop at "please log in" before the study is shown.
- **After the login** (the same session, or a later one): read `nozle-study.yaml` first, run `nozle-check study` (one plain command) and reuse every finding whose files are unchanged; re-read only the files it reports as changed. Then do step 3 (the account read), update `nozle-study.yaml` (`account_read.status: read` and `read_at`; updating it is not editing application code, so do it even when the user said no edits) and each activity's status against the real meters (`matched`, `suggested` or `partial`, see [decision-questions.md](references/decision-questions.md)), and continue at step 5. Do not redo the study, and do not ask the user to repeat anything they already answered.
- **`nozle-study.yaml`** (repository root, allowed by the guards, no secrets): `schema: nozle.study`, `version: 1`, `account_read: { status: not_read | read, read_at }`, `stack`, `existing` (from `nozle-check scan`), `activities` (`id`, `label`, `location` as `path:line`, `status`, optional `proposed_meter`), `linked_services`, `findings` (`id`, `text`, `location`), and `source_files` (`path` and SHA-256 from `nozle-check hash`) for every file the findings rely on. Validate it with `nozle-check nozle-study.yaml`.

## One product, several repositories or sessions

A product is often a backend repository and a frontend repository (or several services), worked on in separate sessions, in one session with several folders open, or in any order. Each repository keeps its own records; what ties them together is the Nozle account (shared) and the `peers` and `interfaces` entries below.

- **Know which part this repository is.** From the stack check: a server that can hold the secret key is a **backend**; a repository with no server code is a **frontend only** (the stack verdict `no-server`). Say which one this is in the first response.
- **Ask where the other part is** (question tool, once): another folder on this machine (ask for the path), another repository that is not available here, or the same session (folders added with the host's add-directory option). Record the answer in `peers: [{ role: backend|frontend, location: <path, repository or "unavailable">, record_seen: true|false }]`.
- **When a peer folder is readable,** read its `nozle.integration.yaml` and `nozle-study.yaml`. A peer that another session works on is read-only here. When this one session has both folders open, keep a record in each repository and edit each only under that repository's own approved scope (the guard judges a peer's files by the peer's record). Reuse its payer and customer mapping, its `decisions` and its `interfaces`; do not ask the user again for what that record already answers, and say what you reused.
- **A backend publishes the contract** the frontend needs, in `interfaces`: `{ id, provides: true, method, route, purpose, shape }` for each route the frontend must call (plans, checkout start, balance, usage, billing portal). The customer always comes from the backend's session, never from the browser. Secret keys exist only in the backend.
- **A frontend only builds against that contract.** With a backend record: `{ id, consumes: true, method, route, status: provided }`. Without one: record each route it needs as `consumes` with `status: unmatched`, build only the presentation and the call sites (no secrets, no direct calls to Nozle with a key), mark the dependent tasks `blocked` with the missing route as the reason, and tell the user which backend work they must do (or ask for it in a backend session). Never invent a backend endpoint inside a frontend repository.
- **Each record describes its own repository:** `selected_goals` lists only the goals built in this repository (a frontend's pricing page is 1, the backend's usage tracking is 5), and `stack` is this repository's own path to Nozle; a frontend with no server leaves `stack` out and reaches Nozle through the backend's `interfaces`.
- **Order does not matter.** Whichever session runs second reads what the first left; a frontend session run first leaves `unmatched` consumes, and the backend session run later reads the frontend's record (if the peer is reachable) and provides them. Each session shows what it reused from the peer.
- **Never assume the peer is done:** `record_seen: false` means unverified, and the first response says so.

## Integrate workflow

1. **Check the stack and dependencies first.** Before the login and before anything else, run `nozle-check env` (as one plain command with the absolute application path: `nozle-check env <path>` where the plugin's bin is on PATH, otherwise `node <skill folder>/scripts/nozle-check.mjs env <path>` using the skill's base directory; never chain it with `cd`, `&&`, `||` or a subshell, because hosts that run without an approver refuse chained commands, and if one form is refused try the other), read the dependency manifests, and confirm the SDK list against the docs MCP. Then tell the user, per part, what Nozle supports on this stack (see [stack-support.md](references/stack-support.md)):
   - **Backend:** any server can integrate: the Node, Python or Go SDK where it applies, otherwise the REST API from the backend in any language (Ruby, PHP, Java, edge runtimes). Name which one and why.
   - **Everything else, stated plainly with what the user owns instead:** the frontend components exist only for React (other frameworks get native components the user owns and styles); automatic LLM capture exists only for OpenAI and Anthropic clients in Node and Python (other providers, other languages and remote AI services need usage reported from the backend); environment blockers such as an ESM-only SDK in a CommonJS project, Node below 18, Python below 3.9 or React below 18.
   - **No server code at all** (a static site, a SPA, a mobile app alone): secret-key work cannot be done here. Ask before any plan or record, with the question tool, and recommend a backend: (1) point to the backend repository (a folder here, or one another session works on) *(recommended: checkout, subscriptions, usage, limits and credits all need the secret key on a server)*; (2) add a server route or SSR adapter to this project; (3) **frontend only for now**: wire only what the browser can do with the publishable key (a pricing page from the public plan catalog, plan and billing screens built against backend routes recorded as `consumes` with `status: unmatched`, their tasks `blocked` until a backend provides them); (4) stop. Do not draft a plan or a record until the user answers. With (3), say plainly which choices stay blocked, leave `stack` out of the record until a backend is chosen, record `peers: [{ role: backend, location: unavailable, record_seen: false }]`, and continue with the study and choices limited to the frontend work.
   Right after the verdict, read `nozle-study.yaml` if it exists (a study from before the login: see "Works without a login") and find what is already there: run `nozle-check scan <path>` (same plain-command rule) and read `nozle.integration.yaml` and `nozle-setup-plan.yaml` if they exist. Report it in the first response as an **Already in place** table: for each of the ten choices, `in place` with file:line (from the scan), `partly` or `not found`, and for a record the tasks completed, pending and blocked (`nozle-check progress`). Existing Nozle code, with or without a record, is the baseline: never rebuild it, never add a second path for the same job (two subscription creators, two usage events for one action); mark it `unverified` until `nozle-doctor` style checks pass, offer to extend or fix it as a delta, and ask only about the gaps. With a record, continue as `nozle-resume` does. Proceed to step 2 only when a backend path exists or the user has chosen how to get one. This verdict binds the build: when the draft record is written (step 5), store it as `stack: { backend_path: node-sdk | python-sdk | go-sdk | rest, runtime: <runtime> }`, and never switch the SDK path or the runtime later without the user's explicit yes and an updated record (the guard refuses an SDK import that contradicts it).
2. **Connect (never blocks the study).** After the stack check passes: if the Nozle account tools are not connected, start the login for this host (see [connect-and-read.md](references/connect-and-read.md)) rather than waiting to be asked. Open dashboard login and choose an organization. When you start the login, tell the user in one line: if their organization isn't onboarded yet, the page offers onboarding, but you can wait only about 5 minutes; for a longer onboarding, finish it first and then log in again (one click, since they're signed in). Account access requires a server-verified onboarded organization and user consent through OAuth. Ask for configuration read; request billing read only when targeted customer or usage evidence is necessary. Never request a pasted Nozle secret key. If account access is unavailable, do not stop: continue with step 4 (the code study), save and show the findings, then explain the blocker, how to log in, and the options (log in now, docs-only, stop). Say which blocker it is: the account tools are not registered yet (ask the user to run the host's MCP login and continue), the login is refused because the organization is not onboarded (the login ends with `onboarding_incomplete` (the user cancelled on the consent page, which lists what is missing) or times out while they onboard: say the account is not onboarded, stop there with no menu, plan or edits, and when the user says onboarding is done, start the login again and continue from step 3), or the server does not offer account access at all (a not-found answer from the account MCP address means this deployment has no account connection: say so, and continue with the code study and a documentation-based plan; the user configures the account in the dashboard). Do not claim account-specific facts from docs.
3. **Read the existing strategy.** Use the account MCP to fetch organization context and all relevant configuration families. Check status and completeness for each family. Summarize the actual plans, meters, entitlements, credits, Cost Sheets, provider connections, and webhook metadata. Ask which offering applies if multiple candidates fit. When the product has its own payment provider, name it, list the providers Nozle supports from the docs MCP (a provider with no guide is unverified), ask which one production uses, and the default is to keep what the product uses today: detect it from the code whatever it is, ask per job it does whether to keep it, replace it or decide later, and never plan a replacement without an explicit yes (see capability 2 and [decision-questions.md](references/decision-questions.md); the options for a new or replacing provider come from the docs MCP and the account read, never from memory). When the product has its own plans, tiers or credit allowances, map them onto Nozle using [plan-design.md](references/plan-design.md) and tell the user what the account can and cannot model, stated in the first response even though the guide is a separate file: per-plan entitlements with numeric limits (a free plan can carry one or two features); plan credit grants that are monthly or yearly (refresh) or lifetime (one-time, inferred as a welcome grant) with no rollover; fixed top-up packages; people as entities under a customer, each able to hold its own subscription, with credits allocated from the customer's paid top-up pool (plan grants cannot be delegated) and a pool policy, but `can()` takes no entity; seats through a recurring unique-count metric fed by the backend; add-ons are priced items that cannot grant credits; credit systems, rates, grant rules and packages are created in the dashboard. Say, for each of the product's tiers, allowances, employee delegation and seats, whether it maps, needs a workaround or has no equivalent. When the deployment lets an organization that is not fully set up connect read-only, empty families are normal and each becomes `needs_account_setup` (a connection refused with `onboarding_incomplete` means that is switched off: tell the user to finish onboarding in the dashboard). Do not stop there. Finish the study and show the choices with what must exist first (for example a meter per billable operation, a plan, a credit system), with a suggestion for each based on the code. The user configures them in the dashboard; you never configure the account and never write an entries file or a setup script for it. Dependent edits do not start until you have re-read the account and the needed items are present, or the user explicitly chooses to continue with them marked pending; independent approved work may proceed.
4. **Inspect the code.** Using the backend and frontend paths from step 1, read the selected application paths. In a monorepo, identify the target app and keep paths inside it. Trace authentication and customer identity, existing payment ownership, service/queue boundaries, AI clients and callers, and tests. Label findings `confirmed` or `inferred` with source locations. Read environment variable names only when needed; avoid credential values. Credit inventory: when the product already spends or manages credits or plan quotas itself, build the complete list before the menu and do not stop at the first deduct call. Spending: every user action that costs credits or consumes a quota (for example buying or enriching leads, starting a campaign, sending, AI generation), with where the check and the deduction happen, how the amount is computed, the identifier (rule, action key, feature, event name), who is charged, and retry and refund behavior. Find them from the data model and seeds (rule and feature tables), every route that guards on a feature or credit check, event consumers that debit from other services, and the frontend's own credit calls; a rule held in the database is read from its seed or migration, and an action you cannot trace is listed as unknown, not omitted. Management: how credits are granted, bought, split, expire, refunded, limited and logged, where balances live, and what the user and admins see, who holds a balance (company pool, per user or per team), how an owner delegates or takes back credits among members and who is allowed to, which balance each spending path draws from, and whether the totals add up. Also list every operation that scales with volume (emails, messages, requests, enrichment lookups, AI generations, invites, storage) and say for each whether credits or quota are deducted per unit today, where the count is taken (per recipient, per message, per request, per batch) and whether a failed or retried unit is counted. Operations that cost something but are not tracked are suggestions, not findings of fault: name the unit, the code point where it would be counted, the suggested treatment (meter, cost-only or leave free) and the reason, and let the user decide. List each spending action on its own row with its own identifier, including the ones the browser reports (do not merge them into one row), and name the exact route or file for each. Delegation: show how an owner assigns, takes back and spends credits among members, which balance each path draws from, and who may do it. Give every spending action a decision: a proposed meter, or an explicit exclusion with its reason. A charge the browser reports (the client sends the amount or the event) gets a proposal for the server route that should own it, with the amount decided on the server, rather than being left out as untrusted. When the product has members, employees or workspaces with their own balances or plans, propose mapping them to entities (allocation, per-person subscriptions, a pool policy) with the supported behavior and limits, and ask. Show this inventory in the first response as a table, one row per spending action, and use it for choices 4, 5, 6 and 10. Linked services: the folder may be one of several services of the same product. Find the calls this code makes to other services (base-URL and queue variables, HTTP and RPC clients, shared database or event names) and list each service that is not in the folder, with what it appears to do (for example AI calls, credit deduction, sending). Ask the user where each one is located (another folder, a repository, or not available) and offer to continue with what is here; mark every conclusion that depends on a missing service `inferred`, and never guess where billable usage or credits are applied. Where the host offers subagents, run read-only `nozle-scanner` agents per area in parallel (see [inspect-stack.md](references/inspect-stack.md)); questions, approvals, and edits stay in the main conversation. Then check the guards: on a host other than Claude Code, if the project has no guard config for it, offer to run `node scripts/nozle-check.mjs hosts <host> --write` (from the skill folder; hosts are codex, cursor, windsurf, gemini, copilot, opencode) and run it only after the user agrees. It creates missing hook and docs-MCP files, never overwrites, and takes effect in the next session, so tell the user to restart the agent (and trust the hooks where the host asks). On Cline it prints a note instead.
5. **Select goals.** Show the choices that apply (exact labels, original numbers; do not paraphrase or merge them; in a table with a `#` column, never a Markdown numbered list, which the terminal renumbers) and offer the left-out ones on request. Accept several goals and free-form outcomes. Ask for them with the question tool (see "Ask with the host's question tool"). Preserve explicit user exclusions. As soon as goals are chosen, write a draft `nozle.integration.yaml` (`schema`, `version`, `organization_id`, `selected_goals`, `stack`, `peers`: the other repositories the user named, or `[]` when this repository is the whole product) in the application repository; the Stop guard asks again when `peers` is missing. Its presence activates the plugin's guards, which refuse application edits until the approved scope is saved in it; the full record is only required at handoff. Trace only the paths needed for selected goals after the bounded first scan.
6. **Map coverage.** Use the support verdict: the SDK where one exists, native components or the REST API where it does not. For each relevant operation, show app location → existing owner or instrumentation → matching Nozle resource → proposed treatment → verification. Treatments include billable usage, cost-only tracking, feature access, UI, synchronization, or exclusion. Mark configuration as verified, missing, incomplete, or unavailable. Classify recommendations as supported, application-owned logic needed, manual setup needed, or unsupported/unverified. Zero additional recommendations is valid. For each selected choice read its guide in `references/capabilities/` (`01-pricing-and-plans.md` through `10-existing-billing-setup.md`); a large repository can use one read-only `nozle-mapper` per choice. Use one primitive per purpose (see runtime-contracts.md): `can()` checks access right before the work and reserves nothing; `usage.track` is the gate and the charge for a credit-backed action and creates the billing event itself, so it is never followed by `track()` for the same action; `track()` records a metered action without credits after it succeeds; Cost Events record serving cost for margin and never bill (SDK: Node `costEvents.track`, Python `cost_events.track`, Go `TrackCostEvent`; LLM wrappers always emit a billable Feature Event, so cost-only tracking cannot use a wrapper). Use [api-map.md](references/api-map.md) to name, for each treatment, the integration surface (SDK method or REST endpoint, with its service) and the file where it plugs in; use REST when the language has no SDK. Call `get_capability_catalog` for the account status, shared prerequisites, and known limits.
7. **Resolve business decisions.** Follow [decision-questions.md](references/decision-questions.md): a specific request asks only what is still open; for every activity found in the code ask the user for a measure decision (never decide one yourself, not even "decide later": when several things are found, the user chooses, with your suggestion first), give a measure decision (`matched` in the account and confirmed, `suggested` with a dashboard step, or `partial`), always allowing "track billable", "cost only", "do not track" and "decide later", grouped by area. Ask at most four related questions at a time with the question tool, and save each answered question to `decisions` in the record (id, question, answer, basis), and put the files of every "do not track" activity in `approved_scope.excluded_paths` (the edit guard enforces it); the handoff record does not validate without the list. Ask about payer identity, selected billable and excluded operations, success/failure/retry/cancel charging, subscription selection, limits, and ownership only when unresolved. Code-discoverable facts are findings. A user request to skip questions does not authorize guesses that change charges or exclusions. An unanswered decision blocks dependent edits; independent approved work may proceed.
8. **Approve concrete scope.** The draft record from step 5 must exist before the scope is shown (write it now if it does not). Before editing application code, show included integration points, exclusions, attribution, financial rules, existing behavior to preserve, phase dependencies, files expected to change, manual prerequisites, effects on current users, and tests. Ask the user, with the question tool, to approve the whole scope or selected phases. Revisit approval only if a material finding changes billing behavior or the agreed boundary. When the plan has a rollout mode (off, shadow, enforce), define each mode exactly in the scope: what is sent to Nozle (real usage events and billing state, advisory checks, or only a log line), which system is authoritative for a denial, and what changes for current users; a log-only stub is not shadow mode unless the user chose it. Present it as a numbered step-by-step plan across all selected choices: each step names its files, its Nozle surface, the manual dashboard steps it needs, and how it is verified. When the user approves the whole scope or tells you to answer open questions yourself, that approves the recommendations you showed: never pick a riskier option for an open decision (charging without payment, letting users with no subscription through, a hard cutover), never redesign an approved item, and ask before any change to an approved item or any edit to a file outside the approved list. Put in the scope every file the billing needs, including the one that supplies a stable id for the usage key (the service that returns the saved row id, or the client code that must send a request or message id), so the build never has to fall back to a random id or a header nobody sends. When the application already holds balances or quotas, the scope must include off, shadow and enforce and a step for every existing balance before enforce: the opening-balance import with a dry run for externally billed subscriptions (capped at the period's plan grant), otherwise a drain the user chooses (legacy balance spent first, then Nozle), because purchased credits have no import; a scope that strands existing balances is incomplete (see financial-rules.md, "Build traps"). For a credit-backed action that can fail after it starts, ask the charge-order question and act on `allowed: false` either way.
9. **Implement by phase.** Save the approved scope before the first edit. Right before the first edit, read the account again (`get_integration_configuration` and the plans with their limits) and drop dashboard steps for items that now exist. Use native tasks and status updates when available; otherwise show the checklist printed by `nozle-check progress`. Write the approved tasks and their `depends_on` to `nozle-tasks.yaml` in the repository root (the guards allow it; a file outside the repository is refused) and run `nozle-check plan` so shared prerequisites appear once and steps are ordered by dependency; paste the result into the integration record. Work one step at a time in that order, and start a step only after its dependencies are completed. A blocked step blocks only its dependents. A completed task needs concrete verification evidence. Do not use Nozle account mutation tools or send billable test events through the plugin.
10. **Verify and hand off.** Report the hand-off in four labelled groups: **Implemented** (code written, with files), **Verified** (what ran, with evidence), **Pending** (dashboard steps and what waits for them), **Not done** (live Nozle calls, deployment, production billing, rollout beyond `off`). Never call it complete or live while anything under Pending or Not done applies; `nozle-status` reports the same groups later, `nozle-undo` backs the changes out. Before handing off, review your own diff against the traps in [financial-rules.md](references/financial-rules.md), fix what you find, and write the result of each check to `self_review` in the record with file and line evidence (see record-format.md; the record does not validate without it): a fresh timestamp on each retry or a 409 treated as charged; an application-side balance that a replayed transaction charges twice or updates without an atomic decrement; an external-billing subscription imported without its opening balance or without a renewal path for the next period, a second subscription imported per period (it makes usage ambiguous), or usage sent without first checking the application's own paid status; entitlements created with POST instead of PATCH; an idempotency or transaction key built from a per-attempt random id or `Date.now()` instead of a business or request id; a 409 detected by message text instead of status; a stream that is not billed when the client aborts after the provider finished, or usage recorded after the final chunk is written; a paid subscription created without checkout or confirmed payment, or more than one code path that creates subscriptions; a schema or model change that breaks queries before its migration runs; an SDK or runtime that differs from the recorded `stack`; one action sent through both `usage.track` and `track()`, or an LLM wrapper plus a manual `track` for the same call; `can()` or `usage.check` used as the gate for a credit-backed action; cost-only tracking done with a wrapper. You usually cannot run the type checker either, so before writing TypeScript read `tsconfig.json` for `strict` and `noUncheckedIndexedAccess`, write to that strictness (no unchecked indexing, no casts between unrelated types), and check each SDK call's types against the SDK's declaration files when they are installed or the docs. If you cannot run the tests, trace each new test through the code path it covers (for example a streaming response that finishes after the handler returns) before handing off, and list every test you could not run as unverified. Run local/fixture tests for approved operations and explicitly excluded paths. A `nozle-verifier` agent can run each step's targeted tests where the host offers one. Inspect mock usage, costs, credit effects, and webhook processing rather than relying only on diffs. Write `nozle.integration.yaml`, `nozle-setup-plan.yaml`, and a readable report using the bundled record format. The integration YAML needs `schema: nozle.integration`, `version: 1`, `organization_id`, `selected_goals`, `configuration` family statuses/revisions, `approved_scope`, `source_files` hashes, and `tasks` with evidence. The setup YAML needs `schema: nozle.setup-plan`, `version: 1`, and `items` with distinct status and evidence. Validate both files with one plain command each: `nozle-check <file>` where the plugin's bin is on PATH, or `node <skill folder>/scripts/nozle-check.mjs <file>` with the skill's absolute base directory (never chained with `cd`, `&&` or `||`). Write the records exactly in the bundled format; if the validator cannot run, do not improvise fields: keep the example's structure and list the records as unvalidated. Separate code implemented, code verified, manual setup pending, awaiting activation, and live result observed.

## Important integration boundaries

- Write no files except the Nozle records, `nozle-study.yaml`, `.env.example` and the approved application files. Plan, spec or design documents from other workflows (a `docs/.../plans/` file, a worktree, a branch) are not part of this skill; the record and the scope are the plan. Do not add them.
- If you cannot or should not build (no server identity to attach a customer to, a missing dependency only the user can provide, a decision they declined), say so plainly, write the record with `blocked: { reason: ... }` and `decisions` (no scope, files or tasks are then required) and stop. A blocked record is a valid hand-off; an incomplete one is not.
- Keep the YAML records parseable: put double quotes around any text value that contains ": " or "#" or starts with a special character. `nozle-check <file>` reports the line and column of a parse error.
- A shared AI client may serve paid and free features. Trace callers before adding a wrapper or proxy. Verify the free paths emit no new billable usage. "Free" does not authorize cost-only tracking; present cost-only and no Nozle events as choices, and leave the path unchanged until the user selects one.
- SDK LLM wrappers can emit feature usage even when detailed cost events are optional. Cost-only tracking uses a separate approved path. Never emit the same consumption twice.
- A check followed by a debit does not establish atomic enforcement of a shared balance plus member cap. Verify a supported primitive or document the product gap.
- Preserve existing payment and subscription ownership. Activation follows authoritative payment confirmation, not a browser redirect.
- When the recorded backend path is an SDK path, add the Nozle SDK you use to the dependency manifest (`package.json`, `requirements.txt`, or the language equivalent) at a version the docs MCP confirms exists, so the build resolves the import. On the REST path no SDK is added (a dependency the code never imports is wrong, and a user instruction to "add the SDK" does not change the verdict: say why). You cannot install it or update the lockfile, so put "run the package manager to install it and refresh the lockfile" in the user's steps.
- Never use, install, configure or recommend `@nozle-js/mcp` (an outdated, undocumented package) or any other Nozle MCP besides the documentation MCP and the account connection this plugin registers; the shell guard refuses commands that name it.
- Never create, ask for, read, or store a Nozle API key. Put the variable names in `.env.example` (empty values), leave `.env` alone, and finish with the dashboard steps the user must do: create the key under Settings > API Keys, copy it into their own `.env`, and complete each missing setup item. Details are in [financial-rules.md](references/financial-rules.md).
- Missing account configuration becomes a manual dashboard step in `nozle-setup-plan.yaml`, with what to configure and why. The user configures the account in the dashboard; you never do it, never write an entries file or a script that does it, and code that needs a missing item waits until a fresh account read shows it. The plugin does not create plans, meters, Cost Sheets, subscriptions, balances, payments, or production usage events.
- Financial suggestions need evidence from current docs, SDK contracts, account configuration, and application code. Label unverified details as such.

# Runtime contracts to verify before editing

Read the live Nozle documentation MCP or linked page again before implementation. Check the **installed SDK version and exports** in the target repository. Nozle's Core and Engine APIs have different base URLs; do not derive an Engine operation from Core OpenAPI alone.

| Need | Verified current contract | Source |
|---|---|---|
| Service URLs | Core: `https://api.nozle.app/core`; Engine: `https://api.nozle.app/engine`. Node SDK 0.11+ sends Feature Events to Engine; `eventsUrl` (Core) serves customers, subscriptions, invoices and usage reads. Node 0.13+, Python 0.13+ and Go v0.12+ take a `host` option (default `https://api.nozle.app`) that fills both; `baseUrl`/`eventsUrl` override it. | [API URLs](https://docs.nozle.dev/guides/getting-started/api-domains.md) |
| Backend credentials | Restricted `sk_` key stays on the merchant backend. Browser `pk_` is for public plan catalog. OAuth plugin access is separate. | [Merchant backend billing](https://docs.nozle.dev/guides/getting-started/merchant-backend-bff.md) |
| Metered event | `nozle.track(customerId, eventCode, metadata, { subscriptionId, transactionId, timestamp })` sends one Feature Event. Multiple active subscriptions require explicit selection. Keep transaction ID and timestamp stable across retries. | [Node tracking events](https://docs.nozle.dev/sdks/node/tracking-events.md) |
| Atomic credits | `nozle.usage.check(...)` is advisory. `nozle.usage.track(input, { idempotencyKey })` atomically consumes and queues the billing event. Keep the same key **and payload** across retries; a denied action remains idempotent. From Engine 2.34.0 a credit hold (`usage.holds.create`, then `finalize` or `release`) reserves credits before work whose cost is known only afterwards. | [Node credits](https://docs.nozle.dev/sdks/node/credits.md), [usage reliability](https://docs.nozle.dev/guides/credits/usage-tracking.md) |
| Team pools | `entity_only`, `entity_then_customer`, and `customer_only` are the documented pool policies. Entity allocation moves eligible purchased credits and preserves provenance; subscription grants are not transferable. A shared fallback does not by itself enforce an unreserved per-member cap. | [Entity credits](https://docs.nozle.dev/guides/credits/entities.md) |
| Top-ups | Paid top-ups are fixed catalog packages; checkout creation does not grant credits. Credits are granted when the top-up invoice is fully paid, by any payment route; a partial payment grants nothing. | [Paid top-ups](https://docs.nozle.dev/guides/credits/top-ups.md) |
| Checkout | `nozle.checkout(customerId, planCode, returnUrl)` returns a discriminated result including `razorpay` (modal), `hosted` (redirect the buyer to `url`; every Stripe checkout), `processing`, `completed`, or `scheduled`. Return origin must be allowlisted by the merchant backend. Browser redirect is not proof of paid activation. | [Node billing](https://docs.nozle.dev/sdks/node/billing.md) |
| LLM wrappers | `wrapOpenAI` and `wrapAnthropic` patch a supplied client instance and emit **one Feature Event** when usage is present; optional `costMeterCode` emits detailed Cost Events. `customerId` is a wrapper option. Tracking is asynchronous and failure does not replace a successful provider response. Use explicit tracking for durable delivery or strict charging. | [Node LLM auto-capture](https://docs.nozle.dev/sdks/node/llm-auto-capture.md) |
| Generic LLM capture | Node 0.13+ `nozle.captureFetch({ customerId, featureCode?, costMeterCode?, onError })` returns a `fetch` for any client that accepts one (OpenAI or Anthropic SDK, Vercel AI SDK providers, LangChain, raw `fetch`); Python 0.13+ `nozle.wrap_http_client(client, customer_id=...)`, `capture_http_client`, `capture_async_http_client` (httpx, `nozle-sdk[httpx]`); Go v0.12+ `WrapHTTPClient(httpClient, nozle, CaptureOptions{...})`. Usage is recognised by response shape (OpenAI-compatible including the Responses API, Anthropic, Gemini), streams included. Same events as the wrappers; the transaction id is the provider response id (`llm-<format>-<id>`). `customerId` can be a function per request, or the request sends `X-Nozle-Customer-Id` (not forwarded); a request with no customer is recorded nowhere, which keeps free callers of a shared client unbilled. No subscription option: the customer needs exactly one active subscription. Wire `onError`: a `feature_not_found` error means the usage is stored but not billed until a metered Feature with that code exists. `recordUsage` / `record_usage` / `RecordUsage` send usage the code read itself. | [Node LLM auto-capture](https://docs.nozle.dev/sdks/node/llm-auto-capture.md), [Python LLM auto-capture](https://docs.nozle.dev/sdks/python/llm-auto-capture.md) |

For a shared AI client, follow the caller graph. A wrapper around the shared instance may emit billable usage for free callers and may bind the wrong customer. Place instrumentation at approved operation boundaries, or use separate instances only after confirming every caller. If the application already tracks a provider call, avoid a second Nozle consumption for the same operation.

For Python and React, load their current SDK pages from the [documentation index](https://docs.nozle.dev/llms.txt) and validate installed versions. React components use the merchant backend for customer billing operations; do not expose secret keys or trust browser supplied customer IDs.

## Usage events, cost events and entitlement checks

Three different primitives. Pick one per purpose and never send two for the same consumption.

| Primitive | What it does | What it does not do | Call | When |
|---|---|---|---|---|
| Feature Event (`track`, Engine) | Records one metered unit for billing aggregation; the code must match a Feature (unknown codes are ignored) | Does not check or deduct credits | Node `track(customerId, event, metadata, { subscriptionId, transactionId, timestamp })`; Python `track(customer_id, event, metadata, subscription_id=, transaction_id=, timestamp=)`; Go `Track(ctx, TrackParams{...})`, batch `Meter` (1-100, subscription id each). Many events: Node `trackBatch(events, { chunkSize, concurrency })` (0.26+), Python `track_batch(events, chunk_size=, concurrency=)` (0.24+), Go `TrackBatch(ctx, []TrackParams, opts...)` (v0.23+): gzipped requests of up to 5000, one result per event (accepted, rejected with its codes, failed: resend with the same transaction id); a lower Engine cap (`too_many_events`) is split and resent. REST `POST /engine/api/v1/events` (`/events/batch`: up to 5000 from Engine 2.28, gzip allowed; the valid events are stored and the refused ones listed by index in `error_details` on a 200; 422/402 only when nothing is stored; a 5xx stores nothing, resend it whole). High volume from many call sites: an event buffer, Node `nozle.createEventBuffer({ onError })` (0.30+), Python `nozle.event_buffer(on_error=)` (0.28+, sync `Nozle` only), Go `client.NewEventBuffer(nozle.EventBufferOptions{OnError: ...})` (v0.27+): `track` returns the transaction id at once with no request, and the buffer sends through the batch call on size (500), timer (5 s) and exit; rejected, failed, full-queue and after-close events go to the error callback | After the operation succeeds, ideally from a durable queue |
| Credit consumption (`usage.track`, Engine) | Atomically converts the metric, deducts credits from eligible sources, records the operation and queues the Core billing event itself | Is not followed by a separate `track()`: that bills twice | Node `usage.track(input, { idempotencyKey })`; Python `usage.track(customer_id, feature_code, ..., idempotency_key=, timestamp=)`; Go `TrackUsage(ctx, params, key)`; REST `POST /engine/api/v1/usage/track` with an `Idempotency-Key` header | Before the work; run the work only when `allowed` is true. `allowed: false` is a product denial (no event), not an error |
| Credit hold (`usage.holds`, Engine 2.34.0+) | Reserves the credits that the most the work can use would cost, on the sources `usage.track` would spend; other callers' checks, tracks, holds and transfers cannot spend them until it is finalized, released or expires (`ttl_seconds`, default 900, at most 86400). `finalize` spends the actual usage as one consume operation (the billing event) at the rate pinned on the hold and releases the rest; `release` frees it | Changes no balance and bills nothing until `finalize`; not followed by a separate `usage.track` or `track()` for the same work | Node 0.30+ `usage.holds.create(params, { idempotencyKey })`, `.finalize(holdId, { properties, timestamp })`, `.release(holdId)`, `.get`, `.list(customerId, { status })`; Python 0.28+ `usage.holds.create(customer_id, feature_code, idempotency_key=, properties=, timestamp=, ttl_seconds=)`, `finalize`, `release`, `get`, `list`; Go v0.27+ `CreateCreditHold(ctx, params, key)`, `FinalizeCreditHold`, `ReleaseCreditHold`, `GetCreditHold`, `ListCreditHolds`; REST `POST /engine/api/v1/usage/holds` (`Idempotency-Key` required), `/usage/holds/{id}/finalize`, `/usage/holds/{id}/release` | Before credit-backed work whose cost is known only after it runs, when several workers spend one balance at once. Run the work only when `allowed` is true; a denial is `allowed: false`, stored under the key |
| Credit check (`usage.check`, Engine) | Advisory projection of the credits an action needs; from Engine 2.34.0 `available` leaves out other callers' open holds | Reserves nothing; never authorizes irreversible work | `usage.check(...)`; REST `POST /engine/api/v1/usage/check` | For display and pre-flight only |
| Entitlement check (`can`, Engine) | Point-in-time access and limit state: `allowed`, `reason`, `used`, `limit`, `remaining` (`limit` and `remaining` are `null` when there is no cap; test with `== null`), `overage`; from Engine 2.34.0 also `reason: "budget_exceeded"` with a `budget` block (`limit`, `spent`, `held`, `remaining`, `currency`, `period_end`, `mode`, `status`, `as_of`) when a hard spend limit is used up | Consumes, reserves and records nothing; may be cached | Node/Python `can(customer, feature, metadata?)`; Go `Can` / `CanWithMetadata`; REST `GET /engine/api/v1/can?customer_id=&feature=` (secret key only) | Right before protected work on the server. Deny with 403, or 429 when `overage` is set (an app convention) |
| Spend limit (budget; Engine 2.34.0, Core 11.23.0, Node 0.30+, Python 0.28+, Go v0.27+) | Caps the gross metered usage charges of one subscription per period in money (`billing_period`, `calendar_month` or `lifetime`), total or per Feature, set on a plan (default) or a subscription (override). `hard` refuses metered usage once `spent + held >= limit`; `soft` only notifies. `can()`, `usage.check` and `usage.track` answer `allowed: false`, `reason: "budget_exceeded"`; the LLM proxy answers 402 `budget_exceeded` before the provider call. Webhooks `budget.threshold_reached` (50/80/90/100 % by default, highest crossed, once per period), `budget.exceeded`, and `usage_limit.threshold_reached` for hard unit limits | Never refuses `POST /events` or `track()`: usage that already happened is always recorded. A plain `can()` is check-then-call: calls in flight and the few seconds of ingest delay can overrun the cap. Not the subscription fee, tax, coupons or credits. No customer-wide cap across subscriptions | Limits: Core REST `/api/v1/spend_limits` (`plan_code` or `external_subscription_id`, `feature_code`, `amount_cents`, `currency`, `period`, `mode`, `thresholds`) or the dashboard; 422 `spend_limit_unrateable_charges` lists covered charges the Engine cannot rate. Standing: Node `budgets.list(customerId, { subscriptionId })`, Python `budgets.list(customer_id, subscription_id=)`, Go `ListBudgets(ctx, customerID, subscriptionID)`; REST `GET /engine/api/v1/customers/{id}/budgets`. Reasons: Node `RefusalReason.BudgetExceeded`, Python `RefusalReason.BUDGET_EXCEEDED`, Go `nozle.RefusalReasonBudgetExceeded`; thrown refusals `BudgetExceededError` (402) and `UsageLimitExceededError` (429) | Set when usage billed in money can run away (AI, sends, API calls). Gate with `can()` right before the work; hold when the cap must be exact |
| Cost Event (Engine) | Records internal serving cost for margin analytics | Never bills the customer | REST `POST /cost-events`: `cost_meter_code`, `parent_transaction_id` or `external_customer_id`, stable `cost_event_id`, `properties` (`tokens`, `provider`, `model`, `type`: input, cached_input, cache_write, output, reasoning), `timestamp` in Unix seconds. Node `costEvents.track`, Python `cost_events.track`, Go `TrackCostEvent`; REST from other languages | After the provider call, using the provider's reported usage; returns 202 and is rated asynchronously |

Patterns:
- **Metered feature without credits:** `can()` right before the work, do the work, `track()` on success with a deterministic transaction id (for example `generation:{id}:completed`), optionally Cost Events linked by `parent_transaction_id`.
- **Credit-backed feature:** `usage.track` is the gate and the charge. Do not add `track()` for the same action, and do not treat `can()` or `usage.check` as the gate. Only Features with `consumable=true` and `count_agg` or `sum_agg` can consume credits.
- **Credit-backed work whose cost is known only afterwards** (an LLM call, an agent run, a long job), with concurrent spenders on one balance: hold the most the work can use, run it only when the hold is `allowed`, `finalize` with the actual usage, and `release` when the work fails or is cancelled. Create the hold with an idempotency key from the unit (run or job id) and keep a fixed `timestamp` on create and on finalize, stored with the unit, so a retry from another process replays; a retried finalize with the same usage replays its first answer, other usage gets 409 `hold_already_resolved`. Finalize above the hold passes only when the free balance covers the difference, otherwise it answers `allowed: false`, charges nothing and leaves the hold open; finalize after expiry runs as a plain track (`hold_expired: true`). A crashed worker's hold frees itself at `expires_at`, so pick a TTL just above the longest run. Through the LLM proxy, the header `X-Nozle-Credit-Hold: <metric amount>` (for example prompt tokens plus `max_tokens`) does the same per request: 402 `insufficient_credits` before the provider is called, `X-Nozle-Credit-Hold-Id` on the response, finalize from the usage the proxy reads. `usage.check` stays advisory; it is not a substitute for a hold.
- **Money caps and unit limits are different refusals** (Engine 2.34.0, Core 11.23.0, Node 0.30+, Python 0.28+, Go v0.27+): `usage_limit_exceeded` means a unit limit (an entitlement cap) is reached, `budget_exceeded` a hard spend limit in money, `insufficient_credits` a credit balance. Compare `reason` (or the error `code`) exactly with the SDK's `RefusalReason` constants, never by searching message or reason text. All three are product refusals: deny the action, show the `budget` or limit, and never retry them; the proxy answers 402 for `budget_exceeded` and `insufficient_credits` and 429 for `usage_limit_exceeded`, and the SDKs raise `BudgetExceededError` / `UsageLimitExceededError` and no longer retry that 429 (older SDKs with retries on do: upgrade or turn retries off for those calls). A 503 `budget_unavailable` or `usage_unavailable` is transient (retry after `Retry-After`, or apply the chosen outage rule). For an exact cap under concurrency, hold first: on a Feature billed in money under a hard limit, `usage.holds.create` reserves the call's estimated spend (`kind: "budget"`, `amount_held`, `currency`; `budget_exceeded` when it does not fit), and `finalize` itself sends the usage event (transaction id `hold:<id>`), so the code sends no `track()` for that work. The proxy's `X-Nozle-Credit-Hold` header does the same.
- **Which way to send Feature Events:** `track()` for one event at a time where the call can wait and the code wants the result; `trackBatch` / `track_batch` / `TrackBatch` for a set of events the code already holds (an import, a queue drain, a settle job), reading the per-event results; an event buffer for high-volume events from many call sites (per request, message or API call) where waiting on Nozle in the request path costs too much. The buffer is in memory only: events still queued are lost when the process is killed, so a serverless handler awaits `flush()` (buffer kept between invocations) or `close()` (buffer per invocation) before it returns, a server calls `close()` on shutdown (Go has no exit hook: `defer buf.Close(ctx)`), and the error callback is wired to logs or a store, never left silent. Give each event its business transaction id (the buffer generates one only when none is passed) so a resend or a second path dedupes in Engine. The buffer is for Feature Events only: credit spends (`usage.track`, holds), and anything whose result decides whether the work runs or what the customer is charged right now, call Nozle directly and read the answer. The LLM wrappers and capture helpers do not use the buffer yet.
- **LLM wrappers and capture** (`wrapOpenAI`/`wrapAnthropic`/`captureFetch`/`recordUsage`, Python `wrap_openai`/`wrap_anthropic`/`wrap_http_client`/`capture_*_http_client`/`record_usage`, Go `Wrap*HTTPClient`/`WrapHTTPClient`/`RecordUsage`) always emit one billable Feature Event (`llm_tokens` by default) and, with a cost meter code, one Cost Event per token type. A wrapped call plus a manual `track` or `usage.track` bills twice. Cost-only tracking therefore cannot use a wrapper: send Cost Events with `external_customer_id`. None of them takes a subscription id, so the customer needs exactly one active subscription. Telemetry is retried only when the client sets `maxRetries` / `max_retries` / `WithMaxRetries`. LiteLLM in Python: capture works only when its HTTP client is routed through Nozle's (OpenAI and Azure providers through `litellm.client_session` / `aclient_session`; other providers per call), and Bedrock usage is not recognised. Without capture (other languages, clients that take no custom `fetch` or HTTP client, responses without a recognised usage shape, remote AI services that return no usage), report the same data manually from the provider's returned usage: the usage call, then one Cost Event per token type linked by `parent_transaction_id` (see capability 7).
- A simple per-event cost can be a Feature Event Cost rule on the Feature instead of Cost Events; each Feature's cost composition (`feature_event_only`, `detailed_events_only`, `add_both`) decides what counts toward margin.
- **Timestamps:** REST takes Unix seconds (milliseconds as decimals); the Node and Python docs show ISO strings, which the SDKs convert. Omitted means reception time.
- **Retries:** the SDKs retry only when configured (Node `maxRetries`, Python `max_retries`, Go `WithMaxRetries`; default 0), and only network errors, timeouts, 429 and 5xx on reads and idempotency-keyed writes; `subscribe` and `checkout` are never retried. An in-process retry is not durable settlement. Reusing a transaction id, idempotency key or `cost_event_id` with a different payload is a conflict (409 on `usage.track`); retry a 503 with the same key after `Retry-After`. After a denial, a new attempt once credits are added uses a new key.
- Do not use the deprecated `checkAndDeduct` / `check_and_deduct` (it skips rates and the ledger and moves the wallet money balance) or the legacy `/cost-models` endpoints.
- React gates (`FeatureGate`, `UsageGate`, `PlanGate`) only display state from the merchant backend; they are not an authorization boundary.

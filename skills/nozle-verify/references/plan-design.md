# Modelling the product's plans in Nozle

Use this when the product already has tiers, credit allowances, seats or add-ons. Compare the product's own plans to the table, say what maps, what needs a workaround, and what Nozle cannot model, then propose exact entries with the reason for each. Mark anything the docs do not state as inferred. Verify against the docs MCP before writing code; the details below were read from the docs and Core on 2026-10-11.

| Need | Nozle | Limits |
|---|---|---|
| Tiered plans: top plan with every feature and high limits, middle plans with lower limits, free plan with one or two features | Plans (API `POST /plans`), features (`POST /features`), and per-plan entitlements (`POST /plans/{code}/entitlements` replaces, `PATCH` adds) with privileges of type integer, boolean, string or select. Runtime check: `can()` | A feature without a cap returns `limit: null` from `can()`. `can()` does not reserve credits. When the catalog has plan families, an entitlement change applies to every plan of the family |
| Plan credit allowance each period | Plan credit grant rule per credit system: monthly, yearly or multi-period; a background sweep (about once a minute) issues the grant to active subscriptions, so it appears shortly after the subscription is active, not instantly | One active rule per plan and credit system. No rollover. An upgrade grants the difference. A downgrade takes effect at the period end by default; the organization's downgrade defaults may apply it at once and revoke unused plan credits, so read the `organization` family before promising either |
| One-time signup credits (for example 20000) on the free plan | A lifetime grant rule on the free plan is the closest match | The docs name no welcome grant: say this is inferred. A lifetime source does not expire |
| Monthly refresh of free credits | A monthly grant rule on the free plan | Each period creates a new balance source that expires at the period boundary |
| Purchased credits | Top-up packages: fixed credits, price, optional expiry; `POST /credit-top-up-purchases`; credits arrive after confirmed payment | Fixed packages only, no arbitrary amounts. Needs a supported payment provider |
| Different credits per action, volume-based use (per email, message, request) | One consumable metric per distinct unit, a rate per metric (credits = units x credit amount / metric amount), consumed with `usage.track` and a stable idempotency key | A rate edit creates a new version. Only count and direct-field sum metrics qualify |
| A company (customer) with many people (employees, members) | Entities under the customer: `PUT /customers/{cust}/entities/{external_id}`, bulk upsert (1-500), suspend, activate. SDK `nozle.entities.*` | Entity lifecycle never emits billing events. Backend with a secret key only |
| A person with their own plan, different from the company and from others | Entity subscriptions: `PUT .../entities/{id}/subscription`, `.../subscription/checkout`, change-plan, cancel. Bulk checkout for up to 100 entities in one invoice. SDK `nozle.entitySubscriptions.*` | The customer pays: one invoice and one payment method for the customer, no entity-level payer or invoice. Bulk checkout needs paid plans of one currency and one interval. One billing anchor per customer, later purchases prorate. An entity with billing history cannot be removed |
| Seats | Price: a fixed charge with units on the plan (`POST /plans/{code}/fixed_charges`), with each subscription's count set by `PUT /subscriptions/{external_id}/fixed_charges/{code}` when members change. Usage view: a recurring unique-count metric fed by add and remove events | No automatic seat billing; entity changes never update units. A seat limit is an entitlement the backend checks before adding a member |
| Credits for one person | Per-entity grant rules (scope `entity`; join policy full_grant, prorated or next_period; leave policy expires the plan grant) and one pool policy per plan and credit system: `entity_only` (hard cap per person), `entity_then_customer` (falls back to the shared pool), `customer_only` | A grant is issued only to the entity that owns the subscription. Not a per-member cap beyond the allocation |
| Owner holds a pool (for example 80000), delegates to employees, who spend, owner takes back | The customer holds paid top-up credits; `credits.allocate` and `credits.deallocate` per entity; employees spend with `usage.track({customerId, entityId})`; balances through `getEntityBalance` (`entity_available`, `shared_available`, `effective_available`) | Only paid top-up value can be allocated, not plan grants. Transfers are switched on per organization and credit system by a Nozle deployment setting; until it is enabled the call returns 403 `credit_transfer_not_enabled`, so tell the user to ask Nozle to enable it. Deallocation returns unused value only. A suspended or deleted entity returns its unused allocation. Allocation is a backend call, not an employee call |
| Per-person feature limits | The entity's subscription is a normal subscription, so plan entitlements attach to it | `can()` takes a customer id and has no entity parameter: per-person gating needs `usage.track` or `usage.check` with `entityId`, or application logic |
| Events attributed to a person | `usage.track` and `usage.check` accept `entityId` | Whether Core events and `/usage/track` carry the entity for invoice-level attribution is not documented: say so |
| Add-ons | One-off priced items | Cannot grant credits, features or seats. Model a recurring extra as a plan, an entitlement or a top-up package |
| Existing provider Nozle does not support | Move to a provider Nozle documents through Nozle checkout (capabilities 2 and 10), with an explicit yes | Without the move, payments, subscriptions and paid-plan credits stay out of the integration; Nozle never mirrors another provider's billing |
| LLM usage | Node `captureFetch` for any client that takes a `fetch` (OpenAI, Anthropic, Vercel AI SDK, LangChain); Python and Go capture through the HTTP client; wrappers for OpenAI and Anthropic clients; cost events from reported tokens | Capture recognises OpenAI-compatible, Anthropic and Gemini usage shapes. A remote AI service is captured only when its response carries one of them; otherwise report usage with `track()` or `POST /cost-events` from the counts it returns, or route it through the Nozle LLM proxy if its base URL can be changed. No counts returned means no capture |

**API or dashboard.** Plans, features, entitlements, add-ons, fixed charges, customers, subscriptions, events, webhook endpoints, entities and usage calls work with a secret key. The docs say credit systems, rates, grant rules, top-up packages and pool policies are configured in the dashboard; Core also has REST routes for them that the docs do not list (`/credit-systems`, `/credit-systems/{code}/rates`, `/credit-systems/{code}/top-up-packages/{code}`, `PUT /plans/{plan}/credit-grants/{system}`, `PUT /plans/{plan}/credit-pool-policies/{system}`), so offer both and say the REST routes are undocumented. The dashboard onboarding can create the whole model at once (features, plans with charges, entitlements, credit systems with rates and top-up packages, grant rules, pool policies, cost sheets, margin policies) for new codes only; it does not cover seats, trials, commitments or percentage fees. Either way the user creates the entries; the agent lists them with exact values.

**Common product shapes.** Use these as starting points, then fit them to the product's own code and price book:
- Seats plus a shared AI credit pool: seat fixed charge, one credit system with a rate per action, a monthly grant per member (entity scope) with `entity_then_customer`, top-up packages, a hard limit on the free plan, premium features entitled on the top plan.
- Usage with included allowance: plan fee plus graduated charges whose first tier is free; `usage_limit` with `hard_limit` on free tiers.
- Prepaid credits only: credit system, lifetime grant on the free plan, top-up packages with `expires_after_days`, a hard stop through `usage.check`.
- Committed spend: a yearly grant drawn down by rates, then graduated overage.
- Outbound or messaging products (email, WhatsApp, LinkedIn, AI generation): one credit system with a rate per channel and AI action, seats as a fixed charge, members as entities, channel add-ons as fixed charges plus entitlement overrides, top-ups with expiry.
What Nozle cannot express: rollover, daily grants, expiry in days on plan grants, manual or promotional grants, auto top-up, low-balance alerts on a credit system (alerts cover subscription usage and wallet balances only, and fire `alert.triggered`), usage reversal, more than one active subscription per customer when credits are used.

**Procedure.** For each product plan, give one row: product plan, Nozle plan, entitlements and limits, credit grant (kind, amount, cadence), seats, add-ons, what has no equivalent. Show tiers from most to least access so the user can check the ladder. Do not create anything: the user creates the entries, and dependent code waits until the account read shows them.
